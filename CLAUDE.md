# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is a Unity project (Editor version pinned in `ProjectSettings/ProjectVersion.txt`, currently `6000.3.10f1` / Unity 6) that doubles as the source repo for **"Useful Toolkit"**, a multi-package UPM (Unity Package Manager) library of game-dev productivity tools authored by Rei. The `Assets/` folder is a throwaway sandbox scene for manually exercising the packages; the actual product is everything under `Packages/com.rei.usefultoolkit.*`. The public source lives at `https://github.com/TaguchiRei/UsefulToolkit.git` (referenced by the in-editor installer — see below), and packages are consumed either via that git URL (`?path=Packages/<name>`) or as local `file:` references (see `Packages/manifest.json`).

There is no npm/CMake/etc. build system — everything is driven through the Unity Editor.

## Commands

There is no CLI build or test pipeline in this repo. All workflows go through the Unity Editor:

- **Open the project**: open this folder with Unity Hub / Unity Editor `6000.3.10f1` (or compatible 6000.x).
- **Compile**: happens automatically when the Editor is open and focused, or via `Assets > Reimport All` / just opening the project. There's no headless build script checked in.
- **Tests**: `com.unity.test-framework` is a project dependency, but no test assembly (`*.Tests.asmdef`) currently exists in any package. If you add tests, run them from `Window > General > Test Runner` in the Editor; there is no CLI test runner configured in this repo.
- **Custom in-editor tools** (menu items, all under the `UsefulToolkit` top menu):
  - `UsefulToolkit/Installer` — opens `UsefulToolkitInstaller` (`Packages/com.rei.usefultoolkit.framework/Editor/Setting/UsefulToolkitInstaller.cs`), a UPM installer window that lets a consumer pick which sub-packages to add via `Client.Add(gitUrl)` against the packages listed above. If you add a new sub-package, add it to `_packages` in that file too. Each `PackageInfo` entry can also declare `RequiredDependencies` — full external UPM identifiers (e.g. git URLs) that get queued automatically whenever that entry (or, for the required `Framework` entry, whenever any package at all) is installed, since UPM does not auto-resolve git-based transitive dependencies from `package.json`. `Framework` currently declares UniTask (`com.cysharp.unitask`) this way, because several of `framework`'s layer asmdefs (`...BlackBoard.Runtime`, `...Application.Runtime`, `...EngineService.Runtime`) reference it directly but it's otherwise undeclared anywhere consumers would see it.
  - `UsefulToolkit/Settings` — opens `UsefulToolkitSettings`, a tabbed settings window whose tabs are auto-discovered via reflection (see Architecture below).
  - `UsefulToolkit/Project Structure` — opens `ProjectStructureWindow` (`Packages/com.rei.usefultoolkit.framework/Editor/ProjectStructure/`), which reorganizes a project's `Assets/` into the toolkit's standard layout: it creates the declared folders, moves/deletes whatever a JSON template's rules match, and can snapshot the current `Assets/` back out as a template. See "Project structure tool" below.
  - `UsefulToolkit/Generate/Scene Enum` — runs `SceneEnumGenerator` (`Packages/com.rei.usefultoolkit.framework/Editor/SceneSupport/`), which regenerates the consumer's `AutoGenerated.BuildScenes` / `NonBuildScenes` enums from the current Build Settings scene list. `[InitializeOnLoad]`, so it also fires automatically on `EditorBuildSettings.sceneListChanged` / new-scene-created when auto-generation is enabled in Settings.
  - `UsefulToolkit/Generate/Scene Compositor` — runs `GameCompositorGenerator` (`Packages/com.rei.usefultoolkit.framework/Editor/Initialize/`), which scans the active scene for `InitializerBase` components (all of them except `UsefulToolkitRuntimeInitializer`) and generates a `<SceneName>Compositor` class. If the scene contains a `UsefulToolkitRuntimeInitializer` it is the **persistent scene**, so the generated class derives `RootGameCompositor<<SceneName>Compositor>` and gets a `RegisterChildBoards` populated with **every** `ChildStateBoardBase`/`ChildEventBoardBase` in the project (minus `SceneBoard`); otherwise it derives `GameCompositor<<SceneName>Compositor>` with no board registration. Either way it fills in `InjectAll` / `InitializeAll` for that scene's Initializers, ordered by `[InitializeOrder]` (ascending, missing = 0) then type FullName. The generated class's `[SerializeField]` fields are assigned by hand in the Inspector. See "Composition root & initialization" below.
  - `UsefulToolkit/Scene/GenerateUsefulPersistentScene` — runs `PersistentSceneCreator` (`Packages/com.rei.usefultoolkit.framework/Editor/Initialize/`), which creates the always-resident boot scene: a `UsefulToolkit System` object carrying `SceneLoader` + `UsefulToolkitRuntimeInitializer`, then (across the domain reload from the Compositor it generates for that scene) has that Compositor component attached automatically. The new-scene flow asks for the scene save path and the **generated-script folder** (Initializers *and* Compositor land there) **separately** (a `SaveFilePanelInProject` then `GameCompositorGenerator.SelectSaveDirectory` — they no longer have to sit in the same folder). If a persistent scene already exists (found by scanning `SceneAsset`s for one that references the `UsefulToolkitRuntimeInitializer` script — no scene is opened during the scan), it skips **both** pickers entirely and, after a single confirm dialog, reopens that scene, tops up any missing `SceneLoader` / `UsefulToolkitRuntimeInitializer` / contributor components, and regenerates its Compositor next to the existing Compositor script (located by class name, falling back to the scene folder) against the current project state; if the scan finds more than one such scene it logs them and falls back to the new-scene flow. Because the scene has a `UsefulToolkitRuntimeInitializer`, the generated Compositor is a `RootGameCompositor<…>` subclass (see above): it builds the shared BlackBoard, registers all project ChildBoards, and its `_startScene` picker (a `[ScenePopup]` over every scene in the project, Build-registered or not) sets the single scene to overwrite-load once initialization finishes. It runs as **three stages separated by domain reloads**, each stage parked in `SessionState` and resumed from `[DidReloadScripts]` (a stage that wrote nothing continues inline instead, since no reload will come):

    1. `InitializerTemplateGenerator.Generate` collects every `IInitializerTemplateProvider` and writes the Initializer sources those declare into the chosen folder — i.e. **into the consumer's assembly**, which is the only place a `<ConcreteCompositor>.TryRegisterContent` call can compile. An existing file of that name is warned about and left alone, so a consumer's edits survive re-runs.
    2. Each generated Initializer type is `AddComponent`ed onto the `UsefulToolkit System` root (found via `TypeCache`, skipped with a warning if it failed to compile), then every `IPersistentSceneContributor` runs (`Editor/Initialize/IPersistentSceneContributor.cs`, also `TypeCache`) so other packages can add and wire their own components on that root without `framework` depending on them. `input` uses both halves: `InputInitializerTemplateProvider` emits the `InputInitializer` subclass, and `InputPersistentSceneContributor` then adds `InputDispatcher` and assigns it into that Initializer's `_inputDispatcher` (reaching it through the abstract `InputInitializerBase`, since the generated type is invisible from the package assembly). Contributors run **after** the Initializers are attached, so they can rely on them being there.
    3. The scene is saved and the Compositor generated, so those `InitializerBase` components are picked up into its `InjectAll` / `InitializeAll`. The Compositor's own `[SerializeField]` fields are still assigned by hand in the Inspector — see `Assets/LocalAssets/UsefulToolkit/CompositorフィールドのInspector割り当てメモ.md` for the open item.
  - `UsefulToolkit/Mesh Cut/Setup` — opens `MeshCutSetupWindow` (`Packages/com.rei.usefultoolkit.meshcut/Editor/`), which builds the `MeshCut System` root (`MeshDataCache` / `FragmentPool` / `CutBlade`) into the open scene and adds `CuttableObject` to the selected objects, moving them under `MeshDataCache`.
  - `UsefulToolkit/AI/*` — `aitool`-package windows: `AiChat` (chat UI), `Generate Default Agents`, and `Unity CLI Loop Installer` (`Packages/com.rei.usefultoolkit.aitool/Editor/CliLoop/UnityCliLoopInstaller.cs`), which automates adding [hatayama/unity-cli-loop](https://github.com/hatayama/unity-cli-loop) (formerly uLoopMCP — a third-party MCP bridge that lets AI agents drive the Unity Editor) via `Client.Add`, running its `uloop-cli` npm CLI and Skills install (`npm install -g uloop-cli`, `uloop skills install --claude|--codex`) through a redirected `cmd.exe` child process, and jumping to that package's own `Window/Unity CLI Loop/Settings` for MCP client config (which this repo intentionally doesn't try to replicate/automate, since it's undocumented and package-version-specific).
  - Per-package menus also exist: `UsefulToolkit/Input/Generate Action Enums`, `UsefulToolkit/ProgramTools/{DebugGUI Setup, MultiFileSearchWindow}`, `UsefulToolkit/WorkTrack/Log Viewer`.
  - `io.github.hatayama.uloopmcp` (the unity-cli-loop MCP bridge) is a direct git dependency of this sandbox project — see `Packages/manifest.json` — so its `uloop` CLI works against this repo out of the box.

## Architecture

### Package layout

Every distributable feature lives under `Packages/com.rei.usefultoolkit.<name>/`, each with its own `package.json`, and `Runtime/` and/or `Editor/` folders. Packages present today:

- `framework` — the core/common package; almost everything else depends on it. No dependencies of its own. It also hosts the State-Centrism **Initialization layer** (the composition root and ordered-initialization base classes): what used to be a separate `architecture` package now lives under `framework/Runtime/Initialization/` + `framework/Runtime/EngineServiceLayer/Initialize/`. There is no `architecture` package anymore — do not look for one.
- `aitool` — Editor-only in-editor AI assistant (chat window, agent/tool commands for Assets/Scene/Inspector/File/Debug), depends on `framework`. **Note:** unlike the other packages, `aitool` is not listed in this project's own `Packages/manifest.json` — it's developed here but not currently consumed by the sandbox project itself. `gitsupport` is also absent from `manifest.json` for the same reason.
- `input` — InputSystem integration and the cleanest end-to-end State-Centrism example (`Runtime/BlackBoardLayer/`, `Runtime/Application/`, `Runtime/EngineServiceLayer/`, `Runtime/Initialization/`); layer-split into its own five layer asmdefs and depends on `framework` only. Input is **State-based, not Event-based** — there is no input EventBoard any more; `InputBoard` is a `ChildStateBoardBase`. The BlackBoard carries the read face only (`IInputState`); the write face (`IInputController`) travels through the DI container. See "Input package" below.
- `worktrack` — Editor-only work-time recorder (session recording, stats, export, its own settings tab). No `Runtime/` folder at all.
- `meshcut` — Burst + Job System mesh slicing, ported from `TaguchiRei/MeshCut`'s `com.rei.usefulmeshcut`. Depends on `framework` (for `UsefulToolkit.Utility`), Burst / Collections / Mathematics, and UniTask. **Not a State-Centrism feature** — it is a standalone library, so it keeps the porting source's `Runtime/{Components, Core, Data, Jobs}` folders under one Runtime asmdef instead of layer folders. See "Mesh cut package" below.
- `debugging` (runtime debug GUI, SceneView info board), `gitsupport` (gitignore/branch helpers, Editor-only), `programtools` (`PauseBoard`, `IPausable`, a multi-file search window) — partially implemented, each depends on `framework`.
- `networking`, `qualitycontroltools`, `soundarttools`, `staticdatatools`, `visualarttools` — each a thin, scaffolded shell (asmdefs + `package.json` only, no `.cs` yet) that depends on `framework`.

`Packages/manifest.json` is the authoritative dependency list for the sandbox project (uses `file:` refs for local packages); `package.json` inside each package is what a real consumer's UPM would resolve when installing via the git-URL path.

### Assembly definition boundaries

Unity draws assembly boundaries at whichever folder has an `.asmdef`. The convention in this repo is one asmdef per `Runtime` and per `Editor` folder per package (e.g. `UsefulToolkit.Framework.Runtime`, `UsefulToolkit.Framework.Editor`). A subsystem that needs to compile as its own assembly (e.g. a State-Centrism layer, see below) gets its own nested asmdef instead of relying on the package's top-level one — check for a closer asmdef before assuming which assembly a new file lands in.

**Assembly names always end with `.Runtime` or `.Editor`, and the layer name (when there is one) goes immediately before that suffix**: `<Project>.<Layer>.Runtime`, falling back to `<Project>.Runtime` / `<Project>.Editor` where no layer is involved. "Project" here is the distribution unit, which inside this repo means `UsefulToolkit.<Package>` — `UsefulToolkit.Framework.BlackBoard.Runtime`, `UsefulToolkit.Debugging.EngineService.Runtime`, `UsefulToolkit.MeshCut.Runtime`, `UsefulToolkit.WorkTrack.Editor`. The package name cannot be dropped from an assembly name: assembly names must be unique across the whole Unity project, and several packages (`framework`, `input`, `debugging`, `programtools`) each carry their own set of per-layer asmdefs. A trailing "Layer" is stripped from the folder name when it becomes the `<Layer>` segment (`BlackBoardLayer` → `BlackBoard`, `EngineServiceLayer` → `EngineService`, `ExternalLayer` → `External`; `Application` and `Initialization` have no suffix to strip). The sandbox under `Assets/Code/Scripts/` follows the same rule with `Sandbox` as the project name (`Sandbox.BlackBoard.Runtime`).

**Namespaces do drop the package name.** `rootNamespace` is `<Project>.<Layer>` — but with `<Project>` meaning the toolkit as a whole, so every package's BlackBoard-layer asmdef declares `rootNamespace` `UsefulToolkit.BlackBoard`, and every `Editor` asmdef declares `UsefulToolkit.Editor`. Actual namespaces then append the feature name (see "Namespace convention" below). Only assembly names distinguish packages; namespaces distinguish layer and feature.

#### Namespace convention

Inside `Packages/`, Runtime code is `UsefulToolkit.<Layer>.<Feature>` and Editor code is `UsefulToolkit.Editor.<Feature>`.

- `<Layer>` is the layer folder with any trailing "Layer" stripped, exactly as in the assembly name.
- `<Feature>` for Runtime is the folder directly under the layer folder — `Runtime/BlackBoardLayer/Scene/` → `UsefulToolkit.BlackBoard.Scene`, `Runtime/Application/Scene/` → `UsefulToolkit.Application.Scene`. Where a layer folder holds `.cs` directly with no feature folder, use the package's feature name instead (`debugging`'s `Runtime/EngineServiceLayer/*.cs` → `UsefulToolkit.EngineService.Debugging`, `programtools`' `Runtime/BlackBoardLayer/*.cs` → `UsefulToolkit.BlackBoard.ProgramTools`).
- `<Feature>` for Editor is the tool for `framework` (`Editor/Initialize/` → `UsefulToolkit.Editor.Initialize`, plus `Attributes` / `Initialize` / `ProjectSettings` / `ProjectStructure` / `Reflection` / `SceneSupport` / `Setting` / `Utility`) and the package itself for single-purpose packages (`UsefulToolkit.Editor.Ai`, `.WorkTrack`, `.GitSupport`, `.MeshCut`, `.Debugging`, `.Input`, `.ProgramTools`).
- The same namespace can be declared from more than one assembly, and that is intended — `UsefulToolkit.Editor.*` spans every package's Editor assembly.

Exceptions that deliberately stay outside this rule: `UsefulToolkit.Utility` (`Runtime/Utility/`, not a layer — see below), `UsefulToolkit.Attributes` (`framework`'s `Runtime/Attributes/`, also not a layer), and the packages that are not layer-split at all, which keep a flat package namespace (`UsefulToolkit.MeshCut`, `UsefulToolkit.Debugging` for `Runtime/DebugGUI.cs`). `input` used to be in that list; it is now layer-split and follows the layer rule (`UsefulToolkit.BlackBoard.Input`, `UsefulToolkit.EngineService.Input`).

**Watch for CS0118 when a namespace segment shadows a type name.** Because layer namespaces sit directly under `UsefulToolkit`, the identifiers `Application`, `Editor`, `Input`, `External` and `BlackBoard` resolve to *namespaces* from anywhere inside `UsefulToolkit.*` whose assembly can see them — which shadows `UnityEngine.Application`, `UnityEditor.Editor` and `UnityEngine.Input`. A compilation-unit-level `using X = ...;` alias does **not** fix this (enclosing-namespace members are checked before compilation-unit aliases); fully qualify instead — `UnityEngine.Application.dataPath`, `UnityEditor.Editor.finishedDefaultHeaderGUI`. Several call sites in `gitsupport`, `programtools` and `framework/Editor/Attributes/MethodExecutorHook.cs` are already written that way for exactly this reason.

`framework`'s `Runtime/` now has one nested asmdef per State-Centrism layer folder, each wired to reference only what the layer table (below) allows it to reference:

| Asmdef | Folder | References |
|---|---|---|
| `UsefulToolkit.Framework.Runtime` | `Runtime/` (now just `Attributes/`, since every layer folder below carves itself out via its own nested asmdef) | *(none)* |
| `UsefulToolkit.Framework.BlackBoard.Runtime` | `Runtime/BlackBoardLayer/` | UniTask (`GUID:f51ebe6a0ceec4240a699833d6309b23`) |
| `UsefulToolkit.Framework.Application.Runtime` | `Runtime/Application/` | `...BlackBoard.Runtime`, `...External.Runtime`, UniTask (same GUID) |
| `UsefulToolkit.Framework.External.Runtime` | `Runtime/ExternalLayer/` | *(none)* |

Every layer folder now holds code: `BlackBoardLayer` has the mediator primitives, `Application`/`ExternalLayer`/`EngineServiceLayer` hold the scene-management system, and `Initialization` holds the composition root. The UniTask references in `...BlackBoard`/`...Application`/`...EngineService` are for that scene-management system.

Two naming exceptions to be aware of: `UsefulToolkit.Utility` does not follow the `<Project>.<Layer>.Runtime` pattern (it is not a State-Centrism layer but a bucket for plain C# helpers that any layer or package may reference — `RecycleBuffer<T>`/`IRecyclable` live there because `meshcut` needs them and they are not mesh-specific), and `Runtime/BlackBoardLayer/Logger/UsefulLogger.cs` is a plain logging utility that happens to live under `BlackBoardLayer/` rather than in `Utility/` — it is not a BlackBoard feature. Every method is `[Conditional]`-gated: `Log` / `LogWarning` / `TemporaryLog` are `UNITY_EDITOR` only, while both `LogError` overloads also carry `[Conditional("DEVELOPMENT_BUILD")]` (the attribute ORs), so errors survive into a development build. The `object`-taking overloads forward that argument to Unity's `context` parameter whenever it is a `UnityEngine.Object`, so clicking the console entry pings the GameObject that logged it; the `Type`-taking ones cannot and do not.

Note: `UsefulToolkit.Framework.EngineService.Runtime` deliberately does **not** reference `...Application.Runtime` or `...Initialization.Runtime` — `Initialization` already references `EngineService`, so a back-reference would be circular. `InitializableMonoBehaviour` (the one base class an EngineServiceLayer `MonoBehaviour` needs) therefore lives *in* `EngineServiceLayer/Initialize/`, even though it declares the namespace `UsefulToolkit.Initialization`. EngineServiceLayer classes that need neither Inspector-serialized fields nor an `Update` loop are written as plain C# classes, not `MonoBehaviour`s.

`input`, `debugging` and `programtools` all carry the full per-layer asmdef skeleton (`<Package>.Application/BlackBoard/External/EngineService/Initialization.Runtime` plus a `<Package>.Runtime` root stub); the layers with no `.cs` yet keep their asmdef anyway so the boundary is already drawn when code arrives. `input`'s `EngineService` asmdef references `UsefulToolkit.Framework.EngineService.Runtime` — that is where `InitializableMonoBehaviour` now lives, so an EngineServiceLayer class no longer has to reference the Initialization asmdef just to derive from it.

### State-Centrism Architecture (actively evolving)

The `framework` package is structured around a "State-Centrism" design: runtime `State` is the single source of truth, organized into layers — Initialization / Application / BlackBoardLayer / ExternalLayer / EngineServiceLayer. This is still an actively-changing design, not a finished one.

**Folder convention**: layer folders live directly under each package's `Runtime/`/`Editor/` (never nested inside a feature folder), and each layer folder contains one subfolder per feature it hosts — i.e. `UsefulToolkit.<package>/Runtime/<Layer>/<Feature>/...`, layer name first, feature name second. The `input` package follows this end-to-end (`Runtime/BlackBoardLayer/`, `Runtime/EngineServiceLayer/`) and is the cleanest reference example.

- `framework`'s top-level `Runtime/` layer folders are `Initialization`, `Application`, `BlackBoardLayer`, `ExternalLayer`, `EngineServiceLayer`. All hold code: `BlackBoardLayer` has the mediator primitives, `Initialization` has the composition root (see "Composition root & initialization" below), and `Application` + `ExternalLayer` + `EngineServiceLayer` (plus the `Scene/` feature folder of `BlackBoardLayer`) hold the scene-management system.
- `BlackBoardLayer` (`Runtime/BlackBoardLayer/`) compiles as one nested asmdef (`UsefulToolkit.Framework.BlackBoard.Runtime`) but splits into three namespaces by feature folder: `UsefulToolkit.BlackBoard.BlackBoard` (`BlackBoard/`, including the `State/` types that used to sit in `UsefulToolkit.Application.StateManagement`), `UsefulToolkit.BlackBoard.Logger` (`Logger/`) and `UsefulToolkit.BlackBoard.Scene` (`Scene/`). It contains:
  - `BlackBoard/Board/` — `BlackBoard.cs` (registers ChildBoards by type; `TryRegister/TryGetStateBoard` and `TryRegister/TryGetEventBoard` use separate dictionaries), `ChildStateBoardBase.cs`, `ChildEventBoardBase.cs`, `BoardDispose.cs` (an Action-backed `IDisposable` used by every Register/Subscribe path in this layer), the scene-scoped-callback machinery `ActionEntry(.cs)` / `ActionEntryList.cs` / `KeyedActionEntryList.cs` (a registered callback carries a `DisposeOnUsed` flag; `ActionEntryList.Invoke()` removes the one-shot entries *before* invoking, and `ActionEntry.Equals` compares only the delegate; `KeyedActionEntryList` inserts a key's `ActionEntryList` only once the first registration has passed validation and **drops the key again the moment that list empties**, whether by unregister or by `DisposeOnUsed` — it re-reads the dictionary before removing, so a re-registration made during an invoke is never discarded), and `HeavyValidationSettings.cs` (an `EditorPrefs`-backed on/off switch for the reflection-heavy validation, so tests can disable it).
  - `BlackBoard/State/` — `StateBase` (abstract `GetLog()`), `StateContext<T>` (change-notification payload, not wired up yet), and the three lifetime base classes `GameStateBase` / `SceneStateBase` / `UnRegistableStateBase`, which are **empty marker classes**: lifetime is expressed purely by which base class a State derives from and which `Register*` overload accepts it. `IStateGetter` (also in `StateBase.cs`) is an empty marker interface used as the dictionary key.
  - `BlackBoard/Event/` — `IEvent` (empty marker interface, the Event-side counterpart of `IStateGetter`) plus three channel implementations and their subscribe-only interfaces: `ActionChannel<T>`/`IActionChannel<T>` (fire-and-forget), `FuncCollectChannel<TArg,TRet>`/`IFuncCollectChannel<,>` (call every handler with the same argument, collect the results into an array), `FuncChainChannel<T>`/`IFuncChainChannel<T>` (pipeline: each handler's return value feeds the next).
  - `BlackBoard/Interface/IBlackBoard.cs`, `BlackBoard/Attributes/RegisterBoardAttribute.cs` (declares on a State which board it gets registered into; validates against `ChildStateBoardBase`), and `Logger/UsefulLogger.cs`.
  - `Scene/` — the BlackBoardLayer half of the scene-management system (see below): `SceneBoard.cs` (an empty ChildBoard), `ISceneState.cs` (the published read + request surface), `SceneState.cs` (the State itself — source of truth for which scenes are loaded), `LoadedSceneSet.cs` (internal — the loaded-scene bookkeeping and the "can I reflect this load/unload" rules, including the persistent-scene set), `SceneLoadRequester.cs` (internal, owned by `SceneState` — turns a request into the minimal load/unload delta, calls the registered loader, reflects the result back), `SceneLoadFunc.cs` (the `SceneLoadFunc` / `SceneUnLoadFunc` named delegates the engine layer plugs into), and `SceneLoadPhase.cs` (`None` / `Loading` / `UnLoading`).
- **`ChildStateBoardBase` and `ChildEventBoardBase` are deliberate 1:1 mirrors of each other.** Both key everything on an interface type (`IStateGetter`-derived / `IEvent`-derived), both expose the same three lifetime scopes, and both share the same exception types and messages:

  | | State side | Event side |
  |---|---|---|
  | ゲーム終了まで | `RegisterGameState<T>(GameStateBase)` | `RegisterGameEvent<T>(IEvent)` |
  | シーンアンロードまで | `RegisterSceneState<T>(SceneStateBase, int sceneId)` | `RegisterSceneEvent<T>(IEvent, int sceneId)` |
  | 手動解除 | `RegisterUnRegistableState<T>(...)` → `IDisposable` | `RegisterUnRegistableEvent<T>(IEvent)` → `IDisposable` |
  | 取得 | `TryGetGameState` / `TryGetSceneState` / `TryGetUnRegistableState` | `TryGetGameEvent` / `TryGetSceneEvent` / `TryGetUnRegistableEvent` |
  | 登録確認 | `CheckRegisterGameState` ほか | `CheckRegisterGameEvent` ほか |
  | 登録の待受 | `SubscribeStateRegister<T>(Action, bool invokeIfRegistered = false)` | `SubscribeEventRegister<T>(Action, bool invokeIfRegistered = false)` |

  One asymmetry is unavoidable: State's `Register*` take a base *class* so the lifetime scope is enforced at compile time, while Event's take `IEvent` (an interface), so the scope is only expressed by the method name. When editing one of these two classes, make the matching change in the other.
- **Publish permission is separated by type, on both channels.** A State's concrete class is held privately by its owner and published only as an `IStateGetter`-derived read interface; a channel's concrete class (`ActionChannel<T>` etc., which owns `Invoke`) is held privately by its publisher and handed out only as the matching `I*Channel<T>` (which exposes `Register` only). Registering a handler always returns an `IDisposable`; `event Action` is deliberately not used, because lambdas registered that way cannot be unsubscribed. All three channels reject a duplicate handler at `Register` time (delegate equality cannot tell two identical registrations apart at unregister time) and snapshot their handler list before invoking, so a handler may Register/Unregister during an invocation. `FuncChainChannel<T>.Register` additionally takes an `int priority` — **ascending, i.e. smaller runs first** (same convention as `InitializeOrderConst` and Unity's `DefaultExecutionOrder`) — and inserts in sorted position at registration time so that equal priorities keep their registration order.
- `IBlackBoard.OnSceneChanged(List<int> sceneIds)` fans out to `SceneBoard` plus **both** ChildBoard dictionaries. Scenes are identified by build index (`int`) everywhere in this system. Each ChildBoard drops only the entries registered under one of those scene ids. Events need this as much as States do: the channel instance itself is held by the board, so a scene-owned publisher would otherwise stay reachable after its scene unloaded. Its one caller is `SceneState` (via `SceneLoadRequester`), right after each unload completes and after the State's own unload callbacks have run.
- **`SceneBoard` is the one ChildBoard that `BlackBoard` special-cases**: it is passed to `BlackBoard`'s constructor and kept in a private field (reachable via `IBlackBoard.GetSceneBoard()`), instead of being registered later via `TryRegisterStateBoard`. It is deliberately *not* also put into the state-ChildBoard dictionary (that would be double bookkeeping), which is why `OnSceneChanged` has to call it separately. The point is that every consumer can assume it exists — other boards' features (running an Action on scene transition, etc.) are expected to depend on the scene State, so it has to be the one thing that is always there. `SceneBoard` itself is an empty `ChildStateBoardBase`; everything scene-related lives on `SceneState`, which `UsefulToolkitRuntimeInitializer` registers into it as `ISceneState` (a game-lifetime State). The read + request surface (`ISceneState`) is reachable from anywhere via `GetSceneBoard().TryGetGameState<ISceneState>(…)`; the engine hookup `SceneState.RegisterSceneLoader(SceneLoadFunc, SceneUnLoadFunc)` is **not** on that interface, so only the code that constructed the concrete `SceneState` (i.e. `UsefulToolkitRuntimeInitializer`) can wire the loader.
- **The scene-management system** spans the ExternalLayer / BlackBoardLayer / Application / EngineServiceLayer / Initialization layers and is the reference example for how a feature crosses them. It was rebuilt from scratch — the earlier `SceneFlowAsset<T>` / `SceneFlow` / `SceneNode` node-graph design and its GraphView editor were **deleted entirely**; do not look for them. Scenes are identified by **build index (`int`)** throughout; the generated `AutoGenerated.BuildScenes` enum (from `SceneEnumGenerator`) is only a typing convenience at call sites.
  - `ExternalLayer/Scene/` — `SceneGroup` (`[Serializable]`) holds exactly **one `bool HasMainScene` and one `int[]` of scene ids**. If `HasMainScene`, `_sceneIds[0]` is the active (lighting/skybox) scene and the rest are additive; otherwise every id is additive and loading the group does not change the active scene. Helpers: `TryGetMainSceneId(out int)`, `AdditiveSceneIds` (an `ArraySegment<int>`, no allocation), `Create<T>(bool hasMainScene, T mainSceneEnum, T[] additiveSceneEnums) where T : Enum`. `SceneGroupDataBase : ScriptableObject, ISerializationCallbackReceiver` is the non-generic base a consumer's asset ultimately derives from (it stores the built `SceneGroup` plus the `_hasMainScene` bool); `SceneGroupDataBase<TSceneEnum> : SceneGroupDataBase where TSceneEnum : Enum` adds the Editor-only `TSceneEnum _mainScene` / `TSceneEnum[] _additionalScenes` fields and rebuilds `SceneGroup` from them in `OnBeforeSerialize`. `SceneGroupDataEditor` (`Editor/SceneSupport/`, `[CustomEditor(typeof(SceneGroupDataBase), true)]`) shows the `_mainScene` enum field only when `_hasMainScene` is ticked — this is the "conditional field" mechanism, done from the Editor assembly because `ExternalLayer` may reference nothing.
  - `BlackBoardLayer/Scene/` — **`SceneState`** is the single source of truth. It derives `GameStateBase`, implements `ISceneState` and `IProgress<float>`, and is registered into `SceneBoard` as `ISceneState` (game lifetime). It holds `ActiveScene` (`int`, `NoSceneId = -1` when none), `AdditiveScenes` (`IReadOnlyList<int>`), `SceneLoadPhase Phase` (`None`/`Loading`/`UnLoading`), `LoadProgress`, and a **persistent-scene set** (scenes that are always "loaded", can never be the active scene, and are never unloaded or demoted — passed to the constructor). Load/unload is requested through `RequestLoadAsync(mainSceneId, subSceneIds)` / `RequestUnLoadAsync(sceneIds)` / `RequestOverwriteLoadAsync(mainSceneId, subSceneIds)` (all `UniTask<bool>`); `RegisterSceneLoader(SceneLoadFunc, SceneUnLoadFunc)` plugs the engine in (concrete-class only, not on `ISceneState`). Change callbacks are `RegisterEventOnLoad` / `OnUnload` / `AnySceneLoaded` / `OnActiveSceneChanged` / `OnPhaseChanged`, each returning `IDisposable` and taking an `ActionEntry`. `LoadedSceneSet` (internal) owns the actual bookkeeping and every "can this load/unload be reflected" rule (with a warning log on rejection); `SceneLoadRequester` (internal, owned by `SceneState`) computes the minimal delta (`CollectLoadTargets` / `CollectUnLoadTargets` / `CollectOverwriteUnloadTargets` — this is where "don't reload an already-loaded scene" lives, **not** in `SceneLoadService`), calls the registered `SceneLoadFunc`/`SceneUnLoadFunc`, and reflects the result back into `SceneState`. `RequestOverwriteLoadAsync` loads the new group first, switches the active scene, then unloads the previous managed scenes (old active scene included, no demotion) that are not in the request and not persistent — `RequestLoadAsync` instead demotes the old active scene to additive and keeps everything already loaded. A `mainSceneId` that is persistent (or otherwise not a legal active-scene target) aborts the whole request **before** the loader runs — the requester asks `SceneState.CanBeActiveScene(id)` first.
  - `Application/Scene/` — `SceneLoadService`, a thin wrapper over a `SceneGroup[]`. `SceneLoadService(IBlackBoard, SceneGroup[])` (the array is cloned); it reads `ISceneState` off `GetSceneBoard()`. `Initialize(int startGroupIndex = 0)` — call once from the persistent-scene-only boot state to overwrite-load the starting group (the persistent scene is the active scene until this runs; a start group with no main scene deliberately leaves it that way). `LoadGroupAsync(int groupIndex, bool overwriteLoadedScenes)` routes to `RequestOverwriteLoadAsync` (丸ごと上書き) or `RequestLoadAsync` (追加ロード); `UnLoadGroupAsync(int groupIndex)`. It is **consumer-constructed and wired** — the framework does not create it. (`SceneManagement.cs` in this folder is a leftover empty class.)
  - `EngineServiceLayer/Scene/` — `SceneLoader : InitializableMonoBehaviour` (namespace `UsefulToolkit.EngineService`), the sole class touching `UnityEngine.SceneManagement.SceneManager`. `LoadScenesAsync(IReadOnlyList<int> sceneIds, int activeSceneId, IProgress<float>, CancellationToken)` additively loads each id then, if `activeSceneId >= 0`, calls `SetActiveScene`; `UnLoadScenesAsync(IReadOnlyList<int>, IProgress<float>, CancellationToken)` unloads each. Both report progress and return `bool`. It is handed to `SceneState` as the `SceneLoadFunc`/`SceneUnLoadFunc` by `UsefulToolkitRuntimeInitializer`.
  - `Initialization/` — `UsefulToolkitRuntimeInitializer : InitializerBase` builds the whole thing: it `new`s a `SceneState` (persistent ids = its own scene's build index, warned if that scene is not in Build Settings, plus an optional `_additionalPersistentSceneIndices` serialized array), registers it as `ISceneState` on `SceneBoard`, then wires the serialized `SceneLoader`'s two methods via `RegisterSceneLoader`. `GameCompositor.Awake` runs it first, before `RegisterChildBoards`, so other Initializers can already use `ISceneState` from their own `Awake`.
  - The `AutoGenerated.BuildScenes` / `NonBuildScenes` enums come from the Editor-side `SceneEnumGenerator` (`Editor/SceneSupport/`), regenerated whenever the Build Settings scene list changes.
  - **Wiring is the consumer's job.** The intended flow: `UsefulToolkit/Scene/GenerateUsefulPersistentScene` makes a resident boot scene whose `RootGameCompositor<…>` subclass runs `UsefulToolkitRuntimeInitializer` (→ `SceneState` + `SceneLoader` live) and registers every project ChildBoard. To leave the boot state there are two paths: set the Compositor's `_startScene` (`[ScenePopup]`) for a no-code single-scene overwrite-load once init finishes, **or** construct `SceneLoadService(blackBoard, groups)` in your own code and call `Initialize(startGroupIndex)` — `_startScene` does not do groups, so anything multi-scene still goes through `SceneLoadService`. Every non-persistent scene gets its own `<SceneName>Compositor : GameCompositor<…>` (Inject/Initialize only, no board registration) and must be entered with the persistent scene already loaded. `Assets/Code/Scripts/` is the sandbox stand-in: one asmdef per layer (`Sandbox.<Layer>.Runtime`), `SceneMarker` (one per scene, shows scene name + seconds alive, to see whether a shared scene was kept or reloaded), `SceneTransitionTester` — a test-only `InitializerBase` wired into the persistent scene's Compositor that drives `ISceneState` and `SceneLoadService` from `OnGUI` buttons — and the **Pause wiring, which is the working demonstration of cross-scene DI**: `PauseState` / `IPauseState` (BlackBoardLayer, carries `[RegisterBoard(typeof(PauseBoard))]`), `PauseManager` / `IPauseManager` (Application — owns the State; `new`ed with no BlackBoard, registers the State in `Initialize(IBlackBoard)`), `PauseInitializer` (persistent scene: `new`s the manager and calls `TryRegisterContent<IPauseManager>` in `Awake`, then `_pauseManager.Initialize(bb)` in `Initialize`), and `PauseButtonInitializer` (`IInjectable<IPauseManager>` + `OnGUI` buttons, placed in **both** `TitleScene` and `InGameScene`). That split — construct and register in `Awake`, initialize in `Initialize` — is what lets a State-owning Application class go through the container at all, since `TryRegisterContent` is `Collection`-phase-only while the BlackBoard only arrives at `Initialize`. Verified in play mode: both scenes' buttons receive the same persistent-scene `PauseManager` through the Root scope. (The old `SceneFlowTestBootstrap` / `SceneFlowTestGui` and the `UsefulToolkit/Test/Setup Scene Flow Test` editor menu are gone, as is the old `CompositorTestScene` harness.)
  - **Generated `<SceneName>Compositor` files live in `Assets/Code/Scripts/Initialization/`, not beside their scenes.** A Compositor must sit in the same assembly as any Initializer that calls `TryRegisterContent`: the Compositor holds each Initializer as a `[SerializeField]` while that Initializer calls `<ConcreteCompositor>.TryRegisterContent<T>(…)`, so the dependency runs both ways and cannot be split across two asmdefs. `Assets/Level` holds level-design assets only and never code, so pointing the generator's save directory at the layer folder is the normal case, not a workaround.

Before writing or reviewing code in this area, treat it as an actively-changing design — folder contents and APIs are still moving.

#### Composition root & initialization

`framework/Runtime/Initialization/` (asmdef `UsefulToolkit.Framework.Initialization.Runtime`, namespace `UsefulToolkit.Initialization`) is the toolkit's cross-package composition root — this is what used to be the `architecture` package.

- The composition root is a **three-level CRTP hierarchy**, one generated `<SceneName>Compositor` per scene (there is no separate `CompositionBase` — `GameCompositor` is the `MonoBehaviour` base):
  - `GameCompositor : MonoBehaviour` (non-generic, `abstract`) — holds `protected static IBlackBoard SharedBlackBoard` plus `TrySetSharedBlackBoard` / `ClearSharedBlackBoard`, and `internal static readonly CompositionContainer Container` — the one DI container every Compositor shares. Exists as the `TypeCache` enumeration point and the legitimately-global slot for both. There is exactly one root, so one shared BlackBoard and one container.
  - `GameCompositor<TSelf> : GameCompositor where TSelf : GameCompositor<TSelf>` (`[DefaultExecutionOrder(InitializeOrderConst.Compositor)]` = **-100**) — the per-scene root. `private static TSelf _instance` and `InitializePhase _phase` are per-closed-type / instance, so two live compositors of different types never clash; `typeof(TSelf)` doubles as this Compositor's **scope key** into the shared `Container`. `Awake` (`protected virtual`): duplicate-`_instance` guard → `_instance = this` → `AbortInitialize` if `SharedBlackBoard == null` (persistent scene not loaded first — aborting rather than merely stopping is what keeps later Initializers from being told the misleading "not in the collection phase") → `_phase = Collection`. `Start` (`protected virtual`): `_phase = Inject` → `InjectAll()` → `_phase = Initialize` → `InitializeAll(SharedBlackBoard)`. `OnDestroy` clears `_instance` and drops this type's container scope (Domain-Reload-off safety). `public static bool TryRegisterContent<T>(T)` (Initializers call it as `<ConcreteCompositor>.TryRegisterContent<T>(x)` — the concrete type name, resolving to `GameCompositor<ConcreteCompositor>`'s static; misuse outside the `Collection` phase is logged — `InitializePhase` is `None`/`Collection`/`Inject`/`Initialize`/`Aborted`) registers into `typeof(TSelf)`'s scope, rejecting a null `instance` — a destroyed `UnityEngine.Object` included, since `is null` alone would pass a fake null through — so a key is never occupied by nothing; a duplicate `T` in **either** that scope or the Root scope is an error that calls `AbortInitialize(reason)` (`_phase = Aborted`, `enabled = false`, one error log carrying the reason), so `InjectAll`/`InitializeAll` never run for that scene — the same type must never reach consumers through two paths. `Aborted` is a distinct phase precisely so that later Initializers registering in the same `Awake` sweep are told the initialization was aborted, rather than the misleading "not in the collection phase". `protected static bool TryGetContent<T>(out T)` (called from the generated `InjectAll`) resolves **own scope → Root scope and nothing else**: sibling scenes can never see each other's registrations, since only the persistent scene is guaranteed to already exist when another scene loads. `private protected static TrySetAsRootScope` / `ClearRootScope` exist for `RootGameCompositor` only. Abstract: `InjectAll` / `InitializeAll`. There is **no** non-generic `GameCompositor.TryRegisterContent`.
  - `RootGameCompositor<TSelf> : GameCompositor<TSelf> where TSelf : RootGameCompositor<TSelf>` — the **persistent scene only**. Adds `[SerializeField] UsefulToolkitRuntimeInitializer _runtimeInitializer`, `[SerializeField] [ScenePopup] string _startScene`, and `abstract RegisterChildBoards(IBlackBoard)`. `Awake`: `new BlackBoard(new SceneBoard())` → `TrySetSharedBlackBoard` (fails+stops if a second root exists) → `TrySetAsRootScope()` (makes this type's container scope the fallback every other Compositor resolves against; on failure it rolls the shared BlackBoard back as well — the two are always set and cleared together, so a half-built root never sits in the shared slot) → `_runtimeInitializer.Initialize(bb)` **first** → `base.Awake()` → `RegisterChildBoards(bb)`. `Start`: `base.Start()` then, if `_startScene` is set, `TransitionToStartSceneAsync().Forget()` — loads that single scene (no group support) via `ISceneState.RequestOverwriteLoadAsync(buildIndex, empty)` when it has a build index, else `#if UNITY_EDITOR` `EditorSceneManager.LoadSceneAsyncInPlayMode` additive + `SetActiveScene` (left untracked by `SceneState`, warned), else error. `OnDestroy` clears `SharedBlackBoard` and the Root scope (only if this instance built it). Both gates — board registration after `base.Awake()`, start-scene transition after `base.Start()` — test `CurrentPhase` (a `private protected` getter on `GameCompositor<TSelf>`), **not** `enabled`: an externally re-enabled Compositor must not transition to the start scene without having been injected.
  - **Board registration lives only in the persistent scene's `RootGameCompositor`.** Every other scene's `<SceneName>Compositor : GameCompositor<…>` is a pure Inject/Initialize unit — it reads the shared BlackBoard and registers nothing. Scene-owned States/Events are registered by that scene's Initializers into the already-present boards, scoped by `gameObject.scene.buildIndex`, and dropped on unload by `IBlackBoard.OnSceneChanged`. Running a non-persistent scene standalone (no persistent scene loaded) is therefore an error by design; use the persistent scene's `_startScene` picker to enter it.
  - **BlackBoard vs. Container — which one carries what.** Read faces go through the BlackBoard: a State's `IStateGetter`-derived interface, an Event channel's `I*Channel<T>` subscribe face. A **write face** — the Application class that owns a State, or an interface exposing its operations — is deliberately *not* put on the BlackBoard (only the Application class that created a State may change it, and an Event channel is a place to register callbacks, not a way to send requests inward). Write faces are handed out through the Container as `IInjectable<T>` dependencies instead, and the Root-scope fallback is what lets a scene receive one built in the persistent scene. Example: the persistent scene's `PauseInitializer` creates `PauseManager`, calls `TryRegisterContent<IPauseManager>(…)`, and registers `PauseState` into `PauseBoard` as `IPauseState`; the InGame and OutGame button Initializers each just implement `IInjectable<IPauseManager>`, and the pause feature never learns which scene's button drives it.
- The `BlackBoard` is **not** put in the DI container — it is passed straight to every `Initialize(IBlackBoard)`.
- `InitializerBase : MonoBehaviour` — `Initialize(IBlackBoard)` + an `Initialized` flag. An Initializer creates the objects other Initializers need and registers them via `<ConcreteCompositor>.TryRegisterContent` in `Awake`, declares its own dependencies by implementing `IInjectable<T>` / `IInjectable<T1,T2>` / … (`Inject(...)` is called during the `Inject` phase), and does its real work in `Initialize`. The premise is that a given concrete Initializer/Compositor type is never run in two scenes at once — if two scenes need the same feature, split the feature into its own scene (or change the init route). `UsefulToolkitRuntimeInitializer` is the one Initializer `RootGameCompositor.Awake` calls directly, and `GameCompositorGenerator` deliberately excludes it from the generated `InitializeAll`.
- **Initializer ordering is declared with `[InitializeOrder(int)]`** (`UsefulToolkit.Attributes`, `framework/Runtime/Attributes/InitializeOrderAttribute.cs`) on the Initializer class. **Ascending — smaller runs first**, same convention as `InitializeOrderConst`, `DefaultExecutionOrder` and `FuncChainChannel`; a type without the attribute is treated as **0**, and ties fall back to type-FullName ordinal so generation stays deterministic. `AttributeUsage` is `Inherited = true`, so a package's abstract Initializer can fix the order for consumers' subclasses. The attribute is read by `GameCompositorGenerator` at generation time only — the ordering is baked into the generated `InjectAll` / `InitializeAll`, so **changing an order means regenerating every affected Compositor**; nothing detects a stale one. Orders other than 0 are emitted as a `// order: N` comment on the generated `Initialize` call. `input`'s **`InputInitializerBase`** carries `InitializeOrderConst.InitializerEarly` (-80) — on the abstract base, which is exactly what `Inherited = true` is for, since the concrete `InputInitializer` is generated into the consumer's assembly and must not have to re-declare it. That keeps the `InputState` it builds in existence before any consumer Initializer that reads it.
- `InitializableMonoBehaviour` (lives in `framework/Runtime/EngineServiceLayer/Initialize/`, namespace `UsefulToolkit.Initialization`) — a `MonoBehaviour` that sets `enabled = false` in `Awake` until `Initialize()` re-enables it. `SceneLoader` derives from it. It has no ordering/`IComparable` member of its own; execution order is expressed with `[DefaultExecutionOrder]` and the `InitializeOrderConst` constants (`Compositor = -100`, `InitializerEarly/-Initializer/-InitializerLate = -80/-70/-60`, `DefaultEarly/-Default/-DefaultLate = -10/0/10`).

### Editor tooling internals

- Settings pages are discovered via reflection, not hard-wired: `SettingPageProvider` (`Framework/Editor/Setting/`) uses `InstanceCollector`/`TypeCollector` (`Framework/Editor/Reflection/`) to find all `SettingPageBase` subclasses and surfaces them as tabs in `UsefulToolkitSettings`. Adding a new settings tab means subclassing `SettingPageBase` — no registration step needed.
- Custom attributes (`ShowOnly`, `PullDownArray`, `SubclassSelector`, `MethodExecutor`, `ScenePopup`) live in `Framework/Runtime/Attributes/` with matching `PropertyDrawer`/hook implementations in `Framework/Editor/Attributes/`. `InitializeOrder` lives in the same folder but is **not** a `PropertyAttribute` and has no drawer — it is read by `GameCompositorGenerator` (see "Composition root & initialization"). `ScenePopup` turns a `string` field into a popup over every scene asset in the project (path-valued, `"(なし)"` = empty), enumerated live from `AssetDatabase` at draw time — no generated candidate list to keep in sync. `PullDownArray` by contrast points at a `static` array member on the same class.
- Project-wide code generation (enum/file generation for scenes etc.) is configured through `UsefulToolkitProjectSettings` / `UsefulToolkitSettingsScriptable`, persisted to `ProjectSettings/UsefulToolkitSettings.asset`. `Framework/Editor/Utility/` has the shared `EnumGenerator` / `FileGenerator` helpers those generators use.
- `Framework/Editor/Initialize/` — the initialization-layer tooling: `GameCompositorGenerator` (`UsefulToolkit/Generate/Scene Compositor`; `GenerateTo(scene, saveDir)` is the dialog-free entry) + `GameCompositorSourceBuilder` (`Build(..., bool isRoot)` builds the `<SceneName>Compositor` source string) + `PersistentSceneCreator` (`UsefulToolkit/Scene/GenerateUsefulPersistentScene`) + `IPersistentSceneContributor` (the extension point `PersistentSceneCreator` enumerates via `TypeCache` right before saving the new scene, so packages `framework` cannot reference — `input` — can still add and wire their own components on the `UsefulToolkit System` root; implementations need a public parameterless ctor and an `Order`) + `IInitializerTemplateProvider` / `InitializerTemplate(Context)` / `InitializerTemplateGenerator` (the same idea one step earlier: a package that needs a `TryRegisterContent` call — which only compiles against the generated Compositor's concrete type — ships an **abstract** Initializer and hands over the source of a thin subclass, which the generator writes into the consumer's assembly; duplicate class names across providers are an error and the later one is dropped, and an existing file is never overwritten) + `PersistentSceneConst`. The generator decides root-ness by `SceneContainsRuntimeInitializer(scene)` (does the scene hold a `UsefulToolkitRuntimeInitializer`); only for a root scene does it collect every `ChildStateBoardBase` / `ChildEventBoardBase` concrete type in the project (minus `SceneBoard`, which `BlackBoard`'s constructor already takes) and emit `RegisterChildBoards`. `CollectInitializerFields` groups the scene's Initializers by concrete type and sorts them by `[InitializeOrder]` then FullName — that sort is the only thing deciding the generated call order, so an Initializer must never assume it runs after another without declaring it. It only warns about the generated file's asmdef references, it does not edit asmdefs.
- `Framework/Editor/SceneSupport/` — `SceneEnumGenerator` (`UsefulToolkit/Generate/Scene Enum`, also `[InitializeOnLoad]` + auto-run on scene-list change) and `SceneGroupDataEditor` (the `SceneGroupDataBase` custom inspector).
- `Framework/Editor/SceneFlowGraph/` and `Framework/Editor/Operator/` are **empty leftover folders** (only `.meta`), from the deleted scene-flow-graph feature. Ignore them; don't recreate files there without a reason.

### Project structure tool

`Framework/Editor/ProjectStructure/` reorganizes a consumer project's `Assets/` (typically a freshly-created Unity project, whose default layout differs per template — URP/2D/HDRP each ship a different set of files) into the toolkit's standard layout. Split across `ProjectStructureTemplate` (data) / `ProjectStructurePath` (path helpers) / `ProjectStructureTemplateIO` (JSON load/save) / `ProjectStructurePlanner` (builds a side-effect-free plan, i.e. the dry run) / `ProjectStructureApplier` (executes it) / `ProjectStructureSnapshot` (current `Assets/` → template) / `ProjectStructureWindow` (IMGUI).

- The template is **JSON, not a ScriptableObject**, so it can be shipped inside the package and carried between projects. `DefaultTemplate.json` sits next to the code and is overridden per-project by `ProjectSettings/UsefulToolkitProjectStructure.json` (kept outside `Assets/` so the tool never processes its own config). Parsed with `JsonUtility`, so **no comments are allowed** — the `description` field is where notes go.
- Rules are `{match, pattern, action, destination}` and are evaluated in the fixed order **ExactPath → Folder → Glob → Name**; a target claimed by an earlier rule (including everything under a claimed folder) is never re-evaluated. That ordering is load-bearing: it is what lets `Assets/Readme.asset`'s Delete rule win over the broad `Assets/*.asset` Glob.
- `excludes` blocks a path from being a move *source* and from snapshot scanning, but still allows it as a *destination* — that's how `Assets/Plugins` receives `TextMesh Pro` while its own contents stay untouched. Unity's special folders (`Resources`, `StreamingAssets`, `Editor`, …) are excluded by default because their location carries meaning.
- Everything goes through `AssetDatabase` (`MoveAsset`/`CreateFolder`/`MoveAssetToTrash`) so `.meta` files and GUID references survive; Delete sends to the OS trash rather than deleting outright. All moves are pre-checked with `ValidateMoveAsset` and **the whole run aborts before any move or delete if a single one fails**.
- Two ordering constraints in the planner are easy to reintroduce as bugs: folders that a folder-move will itself create must *not* be pre-created (`BuildFolderCreations` filters anything same-or-under a move destination, which is why `Assets/Data/Settings` appears in `folders` yet is skipped when `Assets/Settings` is being moved into `Assets/Data`), and moves are topologically ordered by `OrderMoves` so a move whose destination is still occupied by another move's source runs second.
- Snapshot can only emit `Name` rules (the current state doesn't record where anything came from), and it **skips any name that occurs at more than one path**, reporting it as a warning instead of guessing. Re-running it regenerates the `Name`+`Move` rules while preserving hand-written ExactPath/Folder/Glob rules.

### Input package

`Packages/com.rei.usefultoolkit.input/` is the reference example of a feature that crosses every layer. It has been rewritten twice, so treat anything contradicting the below as stale: it used to publish an `InputBoard` of type `ChildEventBoardBase` (gone — `InputBoard` is a `ChildStateBoardBase`), and it used to hang an `IInputDispatcher` off `IInputState` that carried the mutating calls (gone — see the split below).

**The rule that shapes the package: through the BlackBoard you may only read the current state and register input callbacks. Nothing reachable from the BlackBoard can change the State.** The read face `IInputState` goes on the board; the write face `IInputController` is handed out through the Compositor's DI container instead, and only the Application class holds the concrete `InputState`.

- `Runtime/BlackBoardLayer/` (namespace `UsefulToolkit.BlackBoard.Input`) — `InputBoard` (an empty `ChildStateBoardBase`), `InputState`, `InputContext<TValue>` / `InputPhase` (this layer's own phase enum, so the payload never drags `InputSystem` into the BlackBoard), and four interfaces that divide the surface up:
  - **`IInputState`** (`IStateGetter`-derived — the only thing published to the board): `InputEnabled`, `ActiveActionMaps` (`IReadOnlyList<string>`), `IsActionMapActive(Enum)` **and** `IsActionMapActive<TMap>(TMap) where TMap : struct, Enum`, `ReadValue<TValue>(Enum, Enum)`, `RegisterInput<TValue>(Enum, Enum, Action<InputContext<TValue>>)` → `IDisposable`, `RegisterInputAsync<TValue>(…, float? timeoutSeconds = null, CancellationToken)` (waits until an input source is bound to that action; `null` means `UsefulToolkitConst.DefaultTimeoutSeconds` = 5s, and a timeout returns `BoardDispose.Empty` plus a warning), `RegisterEventOnInputEnabledChanged(ActionEntry<StateContext<bool>>)`, `RegisterEventOnActiveActionMapsChanged(ActionEntry)`.
  - **`IInputController`** (never on the board): `SwitchActionMap` / `EnableActionMap` / `DisableActionMap`, `EnableInput` / `DisableInput`, `Bind<TValue>(Enum, Enum)`, `RegisterExternalInputSource<TValue>`. It is defined in the BlackBoardLayer only because that is the one place both Application and EngineService can see (same reason as `IInputEngineBridge`) — **its location is not permission to put it on a board**.
  - **`IInputEngineBridge`** — what an EngineServiceLayer class implements: `ReadValue<TValue>`, `TryCreateInputSource<TValue>`, and **two** reflect-to-engine methods: `Apply(bool inputEnabled, IReadOnlyList<string> activeActionMaps)` is **differential** — it only disables maps not in the list and only enables maps not already on, so an in-progress input on an untouched map is not interrupted (used by `EnableActionMap` / `DisableActionMap` / `EnableInput` / `DisableInput`); `ApplyExclusive(bool, IReadOnlyList<string>)` disables **every** map then re-enables the listed ones, deliberately re-arming even maps that stay active so their in-progress input is cancelled (used by `SwitchActionMap` and by `RegisterInputEngine` on connect, since the engine's pre-connect map state is unknown). There is deliberately **no engine→State path**: the engine cannot push values, it only hands over an input source that `InputState` itself wires to a channel.
  - **`IExternalInputSource<TValue>`** — `RegisterAction` / `UnRegisterAction`. The contract is explicitly **multicast**: `RegisterAction` adds and must not replace, `UnRegisterAction` removes only that handler, a null or unregistered handler is a no-op, and registering the same handler twice is undefined (so callers must not). Both implementations follow it (`InputDispatcher.InputActionSource<T>` subscribes to the `InputAction` on the 0→1 handler transition and unsubscribes on 1→0; `MobileInputEngineService` is a plain `+=` / `-=`).
- `InputState` derives `GameStateBase`, carries `[RegisterBoard(typeof(InputBoard))]`, and implements `IInputState` plus the mutating half:
  - One `ActionChannel<InputContext<TValue>>` per `(map name, action name)` in `_channels`. A channel is **never removed** — a bound input source holds it, so replacing one would silently orphan every handler; the count is capped by the number of `(map, action)` pairs. If a second caller asks for the same pair with a different `TValue`, that is an **error log and a refusal**, not a replacement.
  - `_boundSourceCounts` reference-counts the sources per pair, so wiring both `InputDispatcher` and a touch source to one action and disposing one does not mark it unbound. `Bind` refuses a second bind of the same pair (started/performed/canceled would otherwise fire twice).
  - `RegisterInput*` is deliberately **not** split per phase: one callback receives started/performed/canceled and the consumer branches on `InputContext<TValue>.Phase`.
  - **Null policy, applied consistently**: a query returns a safe default (`IsActionMapActive` → `false`, `ReadValue` → `InputPhase.Disabled`); a command throws `ArgumentNullException`.
  - `RegisterInputEngine(IInputEngineBridge)` is on the concrete class only, not on `IInputState` — same pattern as `SceneState.RegisterSceneLoader`. It pushes the current state into the engine on connect, which is what makes "engine is a mirror" hold from the first frame.
  - **Disposing what `RegisterInput*` returns is the caller's job, by design.** There is no scene-scoped overload: common input often spans scenes, and an `IDisposable` handed out is an `IDisposable` the receiver must release. `IInputState`'s doc points at UniTask's `AddTo(this.GetCancellationTokenOnDestroy())` for callers who want the registration tied to a GameObject.
- **Zero-allocation on the per-frame paths.** `ActionChannel.Invoke` reuses a cached handler snapshot; `EnumNameCache` / `EnumNameCache<TEnum>` (`framework`'s `Runtime/Utility/`) replace `Enum.ToString()`, which allocates ~30 B a call in Mono; `InputDispatcher` caches `(Enum, Enum) → InputAction` so name resolution, the `FindActionMap`/`FindAction` scan and the not-found warning all happen once per pair. The one cost left is at the **call site**: passing an enum literal to an `Enum` parameter boxes it, so a per-frame `ReadValue` should hold `private static readonly Enum` fields (documented on `IInputState.ReadValue`). `IsActionMapActive` needs nothing — its generic overload wins overload resolution automatically.
- `Runtime/Application/` — `IInputManager : IInputController` / `InputManager` (`[Serializable]`, parameterless ctor, since the Initializer holds it by `[SerializeReference]`): `bool Initialize(IBlackBoard, IInputEngineBridge)` creates the `InputState`, hands it the bridge, and registers it into `InputBoard` as `IInputState`; every `IInputController` member is a guarded delegation to that State. It **returns `false` without creating the State** if the bridge is null or `InputBoard` is not registered, and `InputInitializerBase` propagates that by not calling `base.Initialize` (so `Initialized` stays false) — the same "don't report success on failure" rule `UsefulToolkitRuntimeInitializer` follows. **The only class holding the concrete State**, per the "Application creates the State" rule.
- `Runtime/EngineServiceLayer/` — `InputDispatcher : InitializableMonoBehaviour, IInputEngineBridge` (renamed from `InputEngineService`, `.meta` GUID carried over so scene references survived) is the sole class touching `InputActionAsset`, which it holds as a `[SerializeField]`. It has **no BlackBoard reference at all** any more — `Apply` / `ApplyExclusive` (see `IInputEngineBridge` above) are the only entry points; both no-op the map toggling while `inputEnabled` is false, and `Apply` additionally warns for any requested map name that does not resolve (the differential path never calls `FindActionMap`, so that check is done separately). `MobileInputEngineService` is the touch path: it implements `IExternalInputSource<Vector2>` itself and is wired with `SetInput(IInputState, IInputController)` before `Initialize()`, registering through `IInputController.RegisterExternalInputSource` into the same channel `InputDispatcher` feeds — Application cannot tell which source fired.
- `Runtime/Initialization/` — **`InputInitializerBase`**, `abstract`, `[InitializeOrder(InitializeOrderConst.InitializerEarly)]`. Holds `[SerializeField] InputDispatcher` and `[SerializeReference] [SubclassSelector] IInputManager` defaulting to `new InputManager()` (so the Application class is swappable from the Inspector without editing package code), and exposes `protected IInputController Controller`. **Order inside `Initialize` is fixed and load-bearing**: `_inputDispatcher.Initialize()` runs *first*, because `_inputManager.Initialize(blackBoard, _inputDispatcher)` ends up calling `RegisterInputEngine`, which immediately pushes state into the engine — the `InputActionAsset` has to be usable by then.
- The **concrete `InputInitializer` is generated into the consumer's assembly**, not shipped: `TryRegisterContent` only compiles against the generated Compositor's concrete type, which the package cannot see. `Editor/InputInitializerTemplateProvider.cs` emits a thin subclass whose `Awake` does `<Compositor>.TryRegisterContent(Controller)` and whose `Initialize` is where the consumer writes their `Bind` / `SwitchActionMap` calls; `Editor/InputPersistentSceneContributor.cs` then adds `InputDispatcher` to the `UsefulToolkit System` root and assigns it into that Initializer's `_inputDispatcher` (reached through the abstract base, since the generated type is invisible from the package assembly). Assigning the `InputActionAsset` stays manual, as does adding `MobileInputEngineService` (it needs a `GraphicRaycaster`).
- Per-`(map, action)` `Bind` calls are **not** done by the package — they need the consumer's generated enums. `map` / `action` are `System.Enum` across the whole public surface and `InputState` converts them to name strings internally, so no package here depends on a consumer type.
- `Editor/InputActionEnumGenerator.cs` (`UsefulToolkit/Input/Generate Action Enums`) regenerates `ActionMaps` plus one `<Map>Actions` enum per map. It **validates everything before writing anything**, so a rejected asset never leaves a half-updated set of files: a name needing sanitizing is a warning (the runtime lookup uses the original name, so the generated enum would not match it), and two names collapsing to one identifier is an error that aborts the run. `Editor/InputActionAssetPostprocessor.cs` auto-runs it, but **only for the Project-wide Actions asset** — output file names are derived from the enum name alone, so importing a second `.inputactions` would overwrite the first one's files.
- `Assets/Code/Scripts/Initialization/InputStateTester.cs` is the sandbox harness and the working demonstration of the split: it takes `IInputState` off `InputBoard` and `IInputController` via `IInjectable<IInputController>`, then exercises every path from `OnGUI`.

### Mesh cut package

`Packages/com.rei.usefultoolkit.meshcut/` slices several meshes at once with a single plane, entirely inside `[BurstCompile]`d jobs — vertex side classification, face split, cap (cut-face) generation, and collider sampling. Only the parts that require a Unity API (reading Transforms, creating `Mesh`es, placing colliders) stay on the main thread. Ported from `TaguchiRei/MeshCut` (`Packages/com.rei.usefulmeshcut`); the algorithm itself is unmodified, so upstream fixes can be diffed straight across. `README.md` in the package is the user-facing manual and `CHANGELOG.md` records exactly what the port changed.

- **It is not organized by State-Centrism layers.** It is a self-contained library with no State, no BlackBoard involvement, and no place in the layer table, so it keeps the source's `Runtime/{Components, Core, Data, Jobs}` split under a single `UsefulToolkit.MeshCut.Runtime` asmdef. Don't retrofit layer folders onto it.
- Runtime pieces: `MultiMeshCut` (the job chain; `Cut(CuttableObject[], NativePlane)` returns `CutMesh[i*2]` = front, `[i*2+1]` = back), `MultiCutBlade` (a scene component whose own Transform is the blade — position on the plane, `transform.up` the normal — and which applies results to pooled fragments), `MeshDataCache` + `NativeMeshDataStore` (the native mesh registry), `MeshCutObjectPool` (fragment pool), `CuttableObject` (target/fragment marker; also builds sphere colliders by k-means over the sampled points).
- **Every cut target must be a child of `MeshDataCache`** — `Start()` walks its children to register meshes and assign `MeshId`. An object outside it gets no id and produces broken results.
- `RecycleBuffer<T>` / `IRecyclable` are **not** in this package: they were moved to `framework`'s `Runtime/Utility/` (namespace and asmdef `UsefulToolkit.Utility`) during the port because nothing about them is mesh-specific. `MeshCutObjectPool` and `CuttableObject` reach them through that asmdef reference. `RingBuffer<T>` came from the same source project and lives there too, currently unused by any package.
- UniTask is a hard runtime dependency (`MultiMeshCut`/`MultiCutBlade`/`MeshCutObjectPool` await it) and is a git URL, so `package.json` cannot declare it — the `UsefulToolkitInstaller` entry carries it as a `RequiredDependencies` entry instead, the same way `Framework` does.

## Conventions

- `UsefulToolkitInstaller`'s package list (`_packages` in `Packages/com.rei.usefultoolkit.framework/Editor/Setting/UsefulToolkitInstaller.cs`) uses `com.rei.usefultoolkit.*` sub-paths that match the real package folder names 1:1 (Framework, Debugging Tools, Git Support, Program Tools, Ai Agent Tools, Input, Networking, Quality Control Tools, Sound Art Tools, Visual Art Tools, Mesh Cut, Static Data Tools, WorkTrack — there is no `architecture` entry).
