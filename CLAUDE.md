# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is a Unity project (Editor version pinned in `ProjectSettings/ProjectVersion.txt`, currently `6000.3.10f1` / Unity 6) that doubles as the source repo for **"Useful Toolkit"**, a multi-package UPM (Unity Package Manager) library of game-dev productivity tools authored by Rei. The `Assets/` folder is a throwaway sandbox scene for manually exercising the packages; the actual product is everything under `Packages/com.rei.usefultoolkit.*`. The public source lives at `https://github.com/TaguchiRei/UsefulToolkit.git` (referenced by the in-editor installer — see below), and packages are consumed either via that git URL (`?path=Packages/<name>`) or as local `file:` references (see `Packages/manifest.json`).

There is no npm/CMake/etc. build system — everything is driven through the Unity Editor.

## Commands

There is no CLI build or test pipeline in this repo. All workflows go through the Unity Editor:

- **Open the project**: open this folder with Unity Hub / Unity Editor `6000.3.10f1` (or compatible 6000.x).
- **Compile**: happens automatically when the Editor is open and focused, or via `Assets > Reimport All` / just opening the project. There's no headless build script checked in.
- **Tests**: `com.unity.test-framework` is a project dependency, but no test assembly (`*.Tests.asmdef`) currently exists in any package. If you add tests, run them from `Window > General > Test Runner` in the Editor; there is no CLI test runner configured in this repo.
- **Custom in-editor tools** (menu items, all under the `UsefulToolkit` top menu):
  - `UsefulToolkit/Installer` — opens `UsefulToolkitInstaller` (`Packages/com.rei.usefultoolkit.framework/Editor/Setting/UsefulToolkitInstaller.cs`), a UPM installer window that lets a consumer pick which sub-packages to add via `Client.Add(gitUrl)` against the packages listed above. If you add a new sub-package, add it to `_packages` in that file too. Each `PackageInfo` entry can also declare `RequiredDependencies` — full external UPM identifiers (e.g. git URLs) that get queued automatically whenever that entry (or, for the required `Framework` entry, whenever any package at all) is installed, since UPM does not auto-resolve git-based transitive dependencies from `package.json`. `Framework` currently declares UniTask (`com.cysharp.unitask`) this way, because several of `framework`'s layer asmdefs (`...BlackBoard.Runtime`, `...Application.Runtime`, `...EngineAdapter.Runtime`) reference it directly but it's otherwise undeclared anywhere consumers would see it.
  - `UsefulToolkit/Settings` — opens `UsefulToolkitSettings`, a tabbed settings window whose tabs are auto-discovered via reflection (see Architecture below).
  - `UsefulToolkit/Project Structure` — opens `ProjectStructureWindow` (`Packages/com.rei.usefultoolkit.framework/Editor/ProjectStructure/`), which reorganizes a project's `Assets/` into the toolkit's standard layout: it creates the declared folders, moves/deletes whatever a JSON template's rules match, and can snapshot the current `Assets/` back out as a template. See "Project structure tool" below.
  - `UsefulToolkit/Generate/Scene Enum` — runs `SceneEnumGenerator` (`Packages/com.rei.usefultoolkit.framework/Editor/SceneSupport/`), which regenerates the consumer's `AutoGenerated.BuildScenes` / `NonBuildScenes` enums from the current Build Settings scene list. `[InitializeOnLoad]`, so it also fires automatically on `EditorBuildSettings.sceneListChanged` / new-scene-created when auto-generation is enabled in Settings.
  - `UsefulToolkit/Generate/Scene Compositor` — runs `GameCompositorGenerator` (`Packages/com.rei.usefultoolkit.framework/Editor/Initialize/`), which scans the active scene for `InitializerBase` components (all of them except `UsefulToolkitRuntimeInitializer`) and generates a `<SceneName>Compositor` class. If the scene contains a `UsefulToolkitRuntimeInitializer` it is the **persistent scene**, so the generated class derives `RootGameCompositor<<SceneName>Compositor>` and gets a `RegisterChildBoards` populated with **every** `ChildStateBoardBase`/`ChildEventBoardBase` in the project (minus `SceneBoard`); otherwise it derives `GameCompositor<<SceneName>Compositor>` with no board registration. Either way it fills in `InjectAll` / `InitializeAll` for that scene's Initializers, ordered by `[InitializeOrder]` (ascending, missing = 0) then type FullName. The generated class's `[SerializeField]` fields are assigned by hand in the Inspector. See "Composition root & initialization" below.
  - `UsefulToolkit/Scene/GenerateUsefulPersistentScene` — runs `PersistentSceneCreator` (`Packages/com.rei.usefultoolkit.framework/Editor/Initialize/`), which creates the always-resident boot scene: a `UsefulToolkit System` object carrying `SceneLoader` + `UsefulToolkitRuntimeInitializer`, then (across the domain reload from the Compositor it generates for that scene) has that Compositor component attached automatically. The new-scene flow asks for the scene save path and the **Compositor script folder** **separately** (a `SaveFilePanelInProject` then `GameCompositorGenerator.SelectSaveDirectory`). That Compositor folder is also where `UsefulToolkit/Generate/Initializers` writes the templated Initializers (they must share the Compositor's assembly), and this command auto-detects it by class name for re-runs. If a persistent scene already exists (found by scanning `SceneAsset`s for one that references the `UsefulToolkitRuntimeInitializer` script — no scene is opened during the scan), it skips **both** pickers entirely and, after a single confirm dialog, reopens that scene, tops up any missing `SceneLoader` / `UsefulToolkitRuntimeInitializer` / contributor components, and regenerates its Compositor next to the existing Compositor script (located by class name, falling back to the scene folder) against the current project state; if the scan finds more than one such scene it logs them and falls back to the new-scene flow. Because the scene has a `UsefulToolkitRuntimeInitializer`, the generated Compositor is a `RootGameCompositor<…>` subclass (see above): it builds the shared BlackBoard, registers all project ChildBoards, and its `_startScene` picker (a `[ScenePopup]` over every scene in the project, Build-registered or not) sets the single scene to overwrite-load once initialization finishes. **It does not write Initializer sources** — that is a separate step (`UsefulToolkit/Generate/Initializers`, see `InitializerTemplateGenerator` below); run it first so the templated Initializer types are compiled before this command attaches them. This command runs as **two stages separated by one domain reload**, the second parked in `SessionState` and resumed from `[DidReloadScripts]` (if the Compositor source didn't change, no reload comes and it continues inline):

    1. `InitializerTemplateGenerator.CollectDeclaredClassNames` is asked which Initializer classes the `IInitializerTemplateProvider`s declare (names only, nothing written); each such type is `AddComponent`ed onto the `UsefulToolkit System` root (found via `TypeCache`, skipped with a warning pointing at `UsefulToolkit/Generate/Initializers` if it isn't compiled yet), then every `IPersistentSceneContributor` runs (`Editor/Initialize/IPersistentSceneContributor.cs`, also `TypeCache`) so other packages can add and wire their own components on that root without `framework` depending on them. `input` uses both halves: `InputInitializerTemplateProvider` emits the `InputInitializer` subclass (via the separate generate command), and `InputPersistentSceneContributor` then adds `InputDispatcher` and assigns it into that Initializer's `_inputDispatcher` (reaching it through the abstract `InputInitializerBase`, since the generated type is invisible from the package assembly). Contributors run **after** the Initializers are attached, so they can rely on them being there. The scene is then saved and the Compositor generated, so those `InitializerBase` components are picked up into its `InjectAll` / `InitializeAll`.
    2. The generated Compositor component is `AddComponent`ed onto the root and its `_runtimeInitializer` wired. The Compositor's own `[SerializeField]` fields are still assigned by hand in the Inspector — see `Assets/LocalAssets/UsefulToolkit/CompositorフィールドのInspector割り当てメモ.md` for the open item.
  - `UsefulToolkit/Mesh Cut/Setup` — opens `MeshCutSetupWindow` (`Packages/com.rei.usefultoolkit.meshcut/Editor/`), which builds the `MeshCut System` root (`MeshDataCache` / `FragmentPool` / `CutBlade`) into the open scene and adds `CuttableObject` to the selected objects, moving them under `MeshDataCache`.
  - `UsefulToolkit/AI/*` — `aitool`-package windows: `AiChat` (chat UI), `Generate Default Agents`, and `Unity CLI Loop Installer` (`Packages/com.rei.usefultoolkit.aitool/Editor/CliLoop/UnityCliLoopInstaller.cs`), which automates adding [hatayama/unity-cli-loop](https://github.com/hatayama/unity-cli-loop) (formerly uLoopMCP — a third-party bridge that lets AI agents drive the Unity Editor; since V3 it is CLI + Skills only, MCP was removed) via `Client.Add` (unpinned, so it always gets the latest), opening that package's own `Window/Unity CLI Loop/Settings` for its **Install CLI** button (the V3 CLI is a native binary from the package's own installer — the window deliberately does **not** run `npm install -g uloop-cli` any more, since the old npm CLI shadows the V3 one on `PATH`), and running `uloop skills install --claude|--codex [--global]` through a redirected `cmd.exe` child process.
  - Per-package menus also exist: `UsefulToolkit/Input/Generate Action Enums`, `UsefulToolkit/Input/Generate External Input Device`, `UsefulToolkit/ProgramTools/{DebugGUI Setup, MultiFileSearchWindow}`, `UsefulToolkit/WorkTrack/Log Viewer`.
  - `UsefulToolkit/AI Mode` — toggles `AiMode` (see "AI mode" below), which makes the generator menus above run without any modal dialog or file/folder picker. **Turn it on before driving any of those menus from an AI agent** (e.g. via uloop `execute-dynamic-code` + `EditorApplication.ExecuteMenuItem`), otherwise the first dialog blocks the Editor's main thread.
  - `io.github.hatayama.uloopmcp` (unity-cli-loop) is a direct git dependency of this sandbox project, pinned to a release tag (`#v3.14.0`) in `Packages/manifest.json`, so its `uloop` CLI works against this repo out of the box. V3's global `uloop` dispatcher picks the per-project runner from `.uloop/project-runner-pin.json`, which is the one file under `.uloop/` that is tracked in git. V3 renamed the custom-tool API (`[UnityCliLoopTool]` + `UnityCliLoopTool<TSchema, TResponse>` in `io.github.hatayama.UnityCliLoop.ToolContracts`); write new custom tools against that.
  - `uloop export-vfx-graph` / `edit-vfx-graph` / `list-vfx-nodes` — project custom tools from `aitool` (`Packages/com.rei.usefultoolkit.aitool/Editor/VfxGraph/`) that read a VFX Graph as compact Markdown and edit it from a JSON operation list. See "VFX Graph tools" below.

## Architecture

### Package layout

Every distributable feature lives under `Packages/com.rei.usefultoolkit.<name>/`, each with its own `package.json`, and `Runtime/` and/or `Editor/` folders. Packages present today:

- `framework` — the core/common package; almost everything else depends on it. No dependencies of its own. It also hosts the State-Centrism **Initialization layer** (the composition root and ordered-initialization base classes): what used to be a separate `architecture` package now lives under `framework/Runtime/Initialization/` + `framework/Runtime/EngineAdapterLayer/Initialize/`. There is no `architecture` package anymore — do not look for one.
- `aitool` — Editor-only in-editor AI assistant (chat window, agent/tool commands for Assets/Scene/Inspector/File/Debug), depends on `framework`. It is listed in the sandbox's `Packages/manifest.json` (together with `com.unity.visualeffectgraph`, which the sandbox carries only so the VFX Graph tools can be exercised; `aitool` is also in `testables` so its EditMode tests show up in the Test Runner). **Note:** `gitsupport` is not listed in `manifest.json` — it's developed here but not currently consumed by the sandbox project itself.
- `input` — InputSystem integration and the cleanest end-to-end State-Centrism example (`Runtime/BlackBoardLayer/`, `Runtime/Application/`, `Runtime/EngineAdapterLayer/`, `Runtime/Initialization/`); layer-split into its own five layer asmdefs and depends on `framework` only. Input is **State-based, not Event-based** — there is no input EventBoard any more; `InputBoard` is a `ChildStateBoardBase`. The BlackBoard carries the read face only (`IInputState`); the write face (`IInputController`) travels through the DI container. See "Input package" below.
- `worktrack` — Editor-only work-time recorder (session recording, stats, export, its own settings tab). No `Runtime/` folder at all.
- `meshcut` — Burst + Job System mesh slicing, ported from `TaguchiRei/MeshCut`'s `com.rei.usefulmeshcut`. Depends on `framework` (for `UsefulToolkit.Utility`), Burst / Collections / Mathematics, and UniTask. **Not a State-Centrism feature** — it is a standalone library, so it keeps the porting source's `Runtime/{Components, Core, Data, Jobs}` folders under one Runtime asmdef instead of layer folders. See "Mesh cut package" below.
- `debugging` (runtime debug GUI, SceneView info board), `gitsupport` (gitignore/branch helpers, Editor-only), `programtools` (`PauseBoard`, `IPausable`, a multi-file search window) — partially implemented, each depends on `framework`.
- `networking`, `qualitycontroltools`, `soundarttools`, `staticdatatools`, `visualarttools` — each a thin, scaffolded shell (asmdefs + `package.json` only, no `.cs` yet) that depends on `framework`.

`Packages/manifest.json` is the authoritative dependency list for the sandbox project (uses `file:` refs for local packages); `package.json` inside each package is what a real consumer's UPM would resolve when installing via the git-URL path.

### Assembly definition boundaries

Unity draws assembly boundaries at whichever folder has an `.asmdef`. The convention in this repo is one asmdef per `Runtime` and per `Editor` folder per package (e.g. `UsefulToolkit.Framework.Runtime`, `UsefulToolkit.Framework.Editor`). A subsystem that needs to compile as its own assembly (e.g. a State-Centrism layer, see below) gets its own nested asmdef instead of relying on the package's top-level one — check for a closer asmdef before assuming which assembly a new file lands in.

**Assembly names always end with `.Runtime` or `.Editor`, and the layer name (when there is one) goes immediately before that suffix**: `<Project>.<Layer>.Runtime`, falling back to `<Project>.Runtime` / `<Project>.Editor` where no layer is involved. "Project" here is the distribution unit, which inside this repo means `UsefulToolkit.<Package>` — `UsefulToolkit.Framework.BlackBoard.Runtime`, `UsefulToolkit.Debugging.EngineAdapter.Runtime`, `UsefulToolkit.MeshCut.Runtime`, `UsefulToolkit.WorkTrack.Editor`. The package name cannot be dropped from an assembly name: assembly names must be unique across the whole Unity project, and several packages (`framework`, `input`, `debugging`, `programtools`) each carry their own set of per-layer asmdefs. A trailing "Layer" is stripped from the folder name when it becomes the `<Layer>` segment (`BlackBoardLayer` → `BlackBoard`, `EngineAdapterLayer` → `EngineAdapter`, `ExternalLayer` → `External`; `Application` and `Initialization` have no suffix to strip). The sandbox under `Assets/Code/Scripts/` follows the same rule with `Sandbox` as the project name (`Sandbox.BlackBoard.Runtime`).

**Namespaces do drop the package name.** `rootNamespace` is `<Project>.<Layer>` — but with `<Project>` meaning the toolkit as a whole, so every package's BlackBoard-layer asmdef declares `rootNamespace` `UsefulToolkit.BlackBoard`, and every `Editor` asmdef declares `UsefulToolkit.Editor`. Actual namespaces then append the feature name (see "Namespace convention" below). Only assembly names distinguish packages; namespaces distinguish layer and feature.

#### Namespace convention

Inside `Packages/`, Runtime code is `UsefulToolkit.<Layer>.<Feature>` and Editor code is `UsefulToolkit.Editor.<Feature>`.

- `<Layer>` is the layer folder with any trailing "Layer" stripped, exactly as in the assembly name.
- `<Feature>` for Runtime is the folder directly under the layer folder — `Runtime/BlackBoardLayer/Scene/` → `UsefulToolkit.BlackBoard.Scene`, `Runtime/Application/Scene/` → `UsefulToolkit.Application.Scene`. Where a layer folder holds `.cs` directly with no feature folder, use the package's feature name instead (`debugging`'s `Runtime/EngineAdapterLayer/*.cs` → `UsefulToolkit.EngineAdapter.Debugging`, `programtools`' `Runtime/BlackBoardLayer/*.cs` → `UsefulToolkit.BlackBoard.ProgramTools`).
- `<Feature>` for Editor is the tool for `framework` (`Editor/Initialize/` → `UsefulToolkit.Editor.Initialize`, plus `Attributes` / `Initialize` / `ProjectSettings` / `ProjectStructure` / `Reflection` / `SceneSupport` / `Setting` / `Utility`) and the package itself for single-purpose packages (`UsefulToolkit.Editor.Ai`, `.WorkTrack`, `.GitSupport`, `.MeshCut`, `.Debugging`, `.Input`, `.ProgramTools`).
- The same namespace can be declared from more than one assembly, and that is intended — `UsefulToolkit.Editor.*` spans every package's Editor assembly.

Exceptions that deliberately stay outside this rule: `UsefulToolkit.Utility` (`Runtime/Utility/`, not a layer — see below), `UsefulToolkit.Attributes` (`framework`'s `Runtime/Attributes/`, also not a layer), and the packages that are not layer-split at all, which keep a flat package namespace (`UsefulToolkit.MeshCut`, `UsefulToolkit.Debugging` for `Runtime/DebugGUI.cs`). `input` used to be in that list; it is now layer-split and follows the layer rule (`UsefulToolkit.BlackBoard.Input`, `UsefulToolkit.EngineAdapter.Input`).

**Watch for CS0118 when a namespace segment shadows a type name.** Because layer namespaces sit directly under `UsefulToolkit`, the identifiers `Application`, `Editor`, `Input`, `External` and `BlackBoard` resolve to *namespaces* from anywhere inside `UsefulToolkit.*` whose assembly can see them — which shadows `UnityEngine.Application`, `UnityEditor.Editor` and `UnityEngine.Input`. A compilation-unit-level `using X = ...;` alias does **not** fix this (enclosing-namespace members are checked before compilation-unit aliases); fully qualify instead — `UnityEngine.Application.dataPath`, `UnityEditor.Editor.finishedDefaultHeaderGUI`. Several call sites in `gitsupport`, `programtools` and `framework/Editor/Attributes/MethodExecutorHook.cs` are already written that way for exactly this reason.

`framework`'s `Runtime/` now has one nested asmdef per State-Centrism layer folder, each wired to reference only what the layer table (below) allows it to reference:

| Asmdef | Folder | References |
|---|---|---|
| `UsefulToolkit.Framework.Runtime` | `Runtime/` (now just `Attributes/`, since every layer folder below carves itself out via its own nested asmdef) | *(none)* |
| `UsefulToolkit.Framework.BlackBoard.Runtime` | `Runtime/BlackBoardLayer/` | UniTask (`GUID:f51ebe6a0ceec4240a699833d6309b23`) |
| `UsefulToolkit.Framework.Application.Runtime` | `Runtime/Application/` | `...BlackBoard.Runtime`, `...External.Runtime`, UniTask (same GUID) |
| `UsefulToolkit.Framework.External.Runtime` | `Runtime/ExternalLayer/` | *(none)* |
| `UsefulToolkit.Framework.EngineAdapter.Runtime` | `Runtime/EngineAdapterLayer/` (`Initialize/InitializableMonoBehaviour.cs`, `Scene/SceneLoader.cs`) | `...BlackBoard.Runtime`, UniTask (same GUID) |
| `UsefulToolkit.Framework.Initialization.Runtime` | `Runtime/Initialization/` — the composition root: `GameCompositor` + `GameCompositor<TSelf>` + `RootGameCompositor<TSelf>`, `InitializerBase`, `IInjectable<…>`, `InitializePhase`, `CompositionContainer` (internal), `UsefulToolkitRuntimeInitializer` | `UsefulToolkit.Framework.Runtime` (for `Attributes`), all four layer asmdefs above (Initialization is the only layer allowed to see every other layer), `UsefulToolkit.Utility`, UniTask (same GUID) — extend this list if a new framework layer asmdef appears |
| `UsefulToolkit.Utility` | `Runtime/Utility/` (engine-agnostic helpers: `InitializeOrderConst`, `UsefulToolkitConst`, `RecycleBuffer<T>`/`IRecyclable`, `RingBuffer<T>`, `EnumNameCache`/`EnumNameCache<TEnum>`) | *(none)* |

Every layer folder now holds code: `BlackBoardLayer` has the mediator primitives, `Application`/`ExternalLayer`/`EngineAdapterLayer` hold the scene-management system, and `Initialization` holds the composition root. The UniTask references in `...BlackBoard`/`...Application`/`...EngineAdapter` are for that scene-management system.

Two naming exceptions to be aware of: `UsefulToolkit.Utility` does not follow the `<Project>.<Layer>.Runtime` pattern (it is not a State-Centrism layer but a bucket for plain C# helpers that any layer or package may reference — `RecycleBuffer<T>`/`IRecyclable` live there because `meshcut` needs them and they are not mesh-specific), and `Runtime/BlackBoardLayer/Logger/UsefulLogger.cs` is a plain logging utility that happens to live under `BlackBoardLayer/` rather than in `Utility/` — it is not a BlackBoard feature. Every method is `[Conditional]`-gated: `Log` / `LogWarning` / `TemporaryLog` are `UNITY_EDITOR` only, while both `LogError` overloads also carry `[Conditional("DEVELOPMENT_BUILD")]` (the attribute ORs), so errors survive into a development build. The `object`-taking overloads forward that argument to Unity's `context` parameter whenever it is a `UnityEngine.Object`, so clicking the console entry pings the GameObject that logged it; the `Type`-taking ones cannot and do not.

Note: `UsefulToolkit.Framework.EngineAdapter.Runtime` deliberately does **not** reference `...Application.Runtime` or `...Initialization.Runtime` — `Initialization` already references `EngineAdapter`, so a back-reference would be circular. `InitializableMonoBehaviour` (the one base class an EngineAdapterLayer `MonoBehaviour` needs) therefore lives *in* `EngineAdapterLayer/Initialize/`, even though it declares the namespace `UsefulToolkit.Initialization`. EngineAdapterLayer classes that need neither Inspector-serialized fields nor an `Update` loop are written as plain C# classes, not `MonoBehaviour`s.

`input`, `debugging` and `programtools` all carry the full per-layer asmdef skeleton (`<Package>.Application/BlackBoard/External/EngineAdapter/Initialization.Runtime` plus a `<Package>.Runtime` root stub); the layers with no `.cs` yet keep their asmdef anyway so the boundary is already drawn when code arrives. `input`'s `EngineAdapter` asmdef references `UsefulToolkit.Framework.EngineAdapter.Runtime` — that is where `InitializableMonoBehaviour` now lives, so an EngineAdapterLayer class no longer has to reference the Initialization asmdef just to derive from it.

### State-Centrism Architecture (actively evolving)

The `framework` package is structured around a "State-Centrism" design: runtime `State` is the single source of truth, organized into layers — Initialization / Application / BlackBoardLayer / ExternalLayer / EngineAdapterLayer. This is still an actively-changing design, not a finished one.

**Folder convention**: layer folders live directly under each package's `Runtime/`/`Editor/` (never nested inside a feature folder), and each layer folder contains one subfolder per feature it hosts — i.e. `UsefulToolkit.<package>/Runtime/<Layer>/<Feature>/...`, layer name first, feature name second. The `input` package follows this end-to-end (`Runtime/BlackBoardLayer/`, `Runtime/EngineAdapterLayer/`) and is the cleanest reference example.

- `framework`'s top-level `Runtime/` layer folders are `Initialization`, `Application`, `BlackBoardLayer`, `ExternalLayer`, `EngineAdapterLayer`. All hold code: `BlackBoardLayer` has the mediator primitives, `Initialization` has the composition root (see "Composition root & initialization" below), and `Application` + `ExternalLayer` + `EngineAdapterLayer` (plus the `Scene/` feature folder of `BlackBoardLayer`) hold the scene-management system.
- `BlackBoardLayer` (`Runtime/BlackBoardLayer/`) compiles as one nested asmdef (`UsefulToolkit.Framework.BlackBoard.Runtime`) but splits into three namespaces by feature folder: `UsefulToolkit.BlackBoard.BlackBoard` (`BlackBoard/`, including the `State/` types that used to sit in `UsefulToolkit.Application.StateManagement`), `UsefulToolkit.BlackBoard.Logger` (`Logger/`) and `UsefulToolkit.BlackBoard.Scene` (`Scene/`). It contains:
  - `BlackBoard/Board/` — `BlackBoard.cs` (registers ChildBoards by type; `TryRegister/TryGetStateBoard` and `TryRegister/TryGetEventBoard` use separate dictionaries), `ChildStateBoardBase.cs`, `ChildEventBoardBase.cs`, `BoardDispose.cs` (an Action-backed `IDisposable` used by every Register/Subscribe path in this layer), the scene-scoped-callback machinery `ActionEntry(.cs)` / `ActionEntryList.cs` / `KeyedActionEntryList.cs` (a registered callback carries a `DisposeOnUsed` flag; `ActionEntryList.Invoke()` removes the one-shot entries *before* invoking, and `ActionEntry.Equals` compares only the delegate; `KeyedActionEntryList` inserts a key's `ActionEntryList` only once the first registration has passed validation and **drops the key again the moment that list empties**, whether by unregister or by `DisposeOnUsed` — it re-reads the dictionary before removing, so a re-registration made during an invoke is never discarded), and `HeavyValidationSettings.cs` (an `EditorPrefs`-backed on/off switch for the reflection-heavy validation, so tests can disable it).
  - `BlackBoard/State/` — `StateBase` (abstract `GetLog()`), `StateContext<T>` (change-notification payload, not wired up yet), and the three lifetime base classes `GameStateBase` / `SceneStateBase` / `UnRegistableStateBase`, which are **empty marker classes**: lifetime is expressed purely by which base class a State derives from and which `Register*` overload accepts it. `IStateGetter` (also in `StateBase.cs`) is an empty marker interface used as the dictionary key.
  - `BlackBoard/Event/` — `IEvent` (empty marker interface, the Event-side counterpart of `IStateGetter`) plus three channel implementations and their subscribe-only interfaces: `ActionChannel<T>`/`IActionChannel<T>` (fire-and-forget), `FuncCollectChannel<TArg,TRet>`/`IFuncCollectChannel<,>` (call every handler with the same argument, collect the results into an array), `FuncChainChannel<T>`/`IFuncChainChannel<T>` (pipeline: each handler's return value feeds the next).
  - `BlackBoard/Interface/` — `IBlackBoard` (the **read face**: `GetSceneBoard` / `TryGetStateBoard` / `TryGetEventBoard`, safe to hand to any Application / EngineAdapter class) and `IBlackBoardController` (the **management face**: `TryRegisterStateBoard` / `TryRegisterEventBoard` / `OnSceneChanged`, held only by `RootGameCompositor` and `SceneState`). `BlackBoard` implements both; the two deliberately do not inherit from each other, so holding the read face never grants registration or the scene-wide drop. `BlackBoard/Attributes/RegisterBoardAttribute.cs` (declares on a State which board it gets registered into; validates against `ChildStateBoardBase`), and `Logger/UsefulLogger.cs`.
  - `Scene/` — the BlackBoardLayer half of the scene-management system (see below): `SceneBoard.cs` (an empty ChildBoard), `ISceneState.cs` (the published read + request surface), `SceneState.cs` (the State itself — source of truth for which scenes are loaded), `LoadedSceneSet.cs` (internal — the loaded-scene bookkeeping and the "can I reflect this load/unload" rules, including the persistent-scene set), `SceneLoadRequester.cs` (internal, owned by `SceneState` — turns a request into the minimal load/unload delta, calls the registered loader, reflects the result back), `SceneLoadFunc.cs` (the `SceneLoadFunc` / `SceneUnLoadFunc` named delegates the engine layer plugs into), and `SceneLoadPhase.cs` (`None` / `Loading` / `UnLoading`).
- **`ChildStateBoardBase` and `ChildEventBoardBase` are deliberate 1:1 mirrors of each other.** Both key everything on an interface type (`IStateGetter`-derived / `IEvent`-derived), both expose the same three lifetime scopes, and both share the same exception types and messages:

  | | State side | Event side |
  |---|---|---|
  | ゲーム終了まで | `RegisterGameState<T>(GameStateBase)` | `RegisterGameEvent<T>(IEvent)` |
  | シーンアンロードまで | `RegisterSceneState<T>(SceneStateBase, int sceneId)` | `RegisterSceneEvent<T>(IEvent, int sceneId)` |
  | 手動解除 | `RegisterUnRegistableState<T>(...)` → `IDisposable` | `RegisterUnRegistableEvent<T>(IEvent)` → `IDisposable` |
  | 取得 | `TryGetGameState` / `TryGetSceneState` / `TryGetUnRegistableState` | `TryGetGameEvent` / `TryGetSceneEvent` / `TryGetUnRegistableEvent` |
  | 登録確認 | `CheckRegisterGameState` ほか | `CheckRegisterGameEvent` ほか |
  | 登録の待受 | `SubscribeStateRegister<T>(Action, bool invokeIfRegistered = false)` | `SubscribeEventRegister<T>(Action, bool invokeIfRegistered = false)` |

  One asymmetry is unavoidable: State's `Register*` take a base *class* so the lifetime scope is enforced at compile time, while Event's take `IEvent` (an interface), so the scope is only expressed by the method name. When editing one of these two classes, make the matching change in the other.
- **Publish permission is separated by type, on both channels.** A State's concrete class is held privately by its owner and published only as an `IStateGetter`-derived read interface; a channel's concrete class (`ActionChannel<T>` etc., which owns `Invoke`) is held privately by its publisher and handed out only as the matching `I*Channel<T>` (which exposes `Register` only). Registering a handler always returns an `IDisposable`; `event Action` is deliberately not used, because lambdas registered that way cannot be unsubscribed. All three channels reject a duplicate handler at `Register` time (delegate equality cannot tell two identical registrations apart at unregister time) and snapshot their handler list before invoking, so a handler may Register/Unregister during an invocation. `FuncChainChannel<T>.Register` additionally takes an `int priority` — **ascending, i.e. smaller runs first** (same convention as `InitializeOrderConst` and Unity's `DefaultExecutionOrder`) — and inserts in sorted position at registration time so that equal priorities keep their registration order.
- `IBlackBoardController.OnSceneChanged(List<int> sceneIds)` fans out to `SceneBoard` plus **both** ChildBoard dictionaries. Scenes are identified by build index (`int`) everywhere in this system. Each ChildBoard drops only the entries registered under one of those scene ids. Events need this as much as States do: the channel instance itself is held by the board, so a scene-owned publisher would otherwise stay reachable after its scene unloaded. Its one caller is `SceneState` (via `SceneLoadRequester`), right after each unload completes and after the State's own unload callbacks have run — which is why `SceneState`'s constructor takes `IBlackBoardController` rather than `IBlackBoard`.
- **`SceneBoard` is the one ChildBoard that `BlackBoard` special-cases**: it is passed to `BlackBoard`'s constructor and kept in a private field (reachable via `IBlackBoard.GetSceneBoard()`), instead of being registered later via `TryRegisterStateBoard`. It is deliberately *not* also put into the state-ChildBoard dictionary (that would be double bookkeeping), which is why `OnSceneChanged` has to call it separately. The point is that every consumer can assume it exists — other boards' features (running an Action on scene transition, etc.) are expected to depend on the scene State, so it has to be the one thing that is always there. `SceneBoard` itself is an empty `ChildStateBoardBase`; everything scene-related lives on `SceneState`, which `UsefulToolkitRuntimeInitializer` registers into it as `ISceneState` (a game-lifetime State). The read + request surface (`ISceneState`) is reachable from anywhere via `GetSceneBoard().TryGetGameState<ISceneState>(…)`; the engine hookup `SceneState.RegisterSceneLoader(SceneLoadFunc, SceneUnLoadFunc)` is **not** on that interface, so only the code that constructed the concrete `SceneState` (i.e. `UsefulToolkitRuntimeInitializer`) can wire the loader.
- **The scene-management system** spans the ExternalLayer / BlackBoardLayer / Application / EngineAdapterLayer / Initialization layers and is the reference example for how a feature crosses them. It was rebuilt from scratch — the earlier `SceneFlowAsset<T>` / `SceneFlow` / `SceneNode` node-graph design and its GraphView editor were **deleted entirely**; do not look for them. Scenes are identified by **build index (`int`)** throughout; the generated `AutoGenerated.BuildScenes` enum (from `SceneEnumGenerator`) is only a typing convenience at call sites.
  - `ExternalLayer/Scene/` — `SceneGroup` (`[Serializable]`) holds exactly **one `bool HasMainScene` and one `int[]` of scene ids**. If `HasMainScene`, `_sceneIds[0]` is the active (lighting/skybox) scene and the rest are additive; otherwise every id is additive and loading the group does not change the active scene. Helpers: `TryGetMainSceneId(out int)`, `AdditiveSceneIds` (an `ArraySegment<int>`, no allocation), `Create<T>(bool hasMainScene, T mainSceneEnum, T[] additiveSceneEnums) where T : Enum`. `SceneGroupDataBase : ScriptableObject, ISerializationCallbackReceiver` is the non-generic base a consumer's asset ultimately derives from (it stores the built `SceneGroup` plus the `_hasMainScene` bool); `SceneGroupDataBase<TSceneEnum> : SceneGroupDataBase where TSceneEnum : Enum` adds the Editor-only `TSceneEnum _mainScene` / `TSceneEnum[] _additionalScenes` fields and rebuilds `SceneGroup` from them in `OnBeforeSerialize`. `SceneGroupDataEditor` (`Editor/SceneSupport/`, `[CustomEditor(typeof(SceneGroupDataBase), true)]`) shows the `_mainScene` enum field only when `_hasMainScene` is ticked — this is the "conditional field" mechanism, done from the Editor assembly because `ExternalLayer` may reference nothing.
  - `BlackBoardLayer/Scene/` — **`SceneState`** is the single source of truth. It derives `GameStateBase`, implements `ISceneState` and `IProgress<float>`, and is registered into `SceneBoard` as `ISceneState` (game lifetime). It holds `ActiveScene` (`int`, `NoSceneId = -1` when none), `AdditiveScenes` (`IReadOnlyList<int>`), `SceneLoadPhase Phase` (`None`/`Loading`/`UnLoading`), `LoadProgress`, and a **persistent-scene set** (scenes that are always "loaded", can never be the active scene, and are never unloaded or demoted — passed to the constructor). Load/unload is requested through `RequestLoadAsync(mainSceneId, subSceneIds)` / `RequestUnLoadAsync(sceneIds)` / `RequestOverwriteLoadAsync(mainSceneId, subSceneIds)` (all `UniTask<bool>`); `RegisterSceneLoader(SceneLoadFunc, SceneUnLoadFunc)` plugs the engine in (concrete-class only, not on `ISceneState`). Change callbacks are `RegisterEventOnLoad` / `OnUnload` / `AnySceneLoaded` / `OnActiveSceneChanged` / `OnPhaseChanged`, each returning `IDisposable` and taking an `ActionEntry`. `LoadedSceneSet` (internal) owns the actual bookkeeping and every "can this load/unload be reflected" rule (with a warning log on rejection); `SceneLoadRequester` (internal, owned by `SceneState`) computes the minimal delta (`CollectLoadTargets` / `CollectUnLoadTargets` / `CollectOverwriteUnloadTargets` — this is where "don't reload an already-loaded scene" lives, **not** in `SceneLoadService`), calls the registered `SceneLoadFunc`/`SceneUnLoadFunc`, and reflects the result back into `SceneState`. `RequestOverwriteLoadAsync` loads the new group first, switches the active scene, then unloads the previous managed scenes (old active scene included, no demotion) that are not in the request and not persistent — `RequestLoadAsync` instead demotes the old active scene to additive and keeps everything already loaded. A `mainSceneId` that is persistent (or otherwise not a legal active-scene target) aborts the whole request **before** the loader runs — the requester asks `SceneState.CanBeActiveScene(id)` first.
  - `Application/Scene/` — `SceneLoadService`, a thin wrapper over a `SceneGroup[]`. `SceneLoadService(IBlackBoard, SceneGroup[])` (the array is cloned); it reads `ISceneState` off `GetSceneBoard()`. `Initialize(int startGroupIndex = 0)` — call once from the persistent-scene-only boot state to overwrite-load the starting group (the persistent scene is the active scene until this runs; a start group with no main scene deliberately leaves it that way). `LoadGroupAsync(int groupIndex, bool overwriteLoadedScenes)` routes to `RequestOverwriteLoadAsync` (丸ごと上書き) or `RequestLoadAsync` (追加ロード); `UnLoadGroupAsync(int groupIndex)`. It is **consumer-constructed and wired** — the framework does not create it. (`SceneManagement.cs` in this folder is a leftover empty class.)
  - `EngineAdapterLayer/Scene/` — `SceneLoader : InitializableMonoBehaviour` (namespace `UsefulToolkit.EngineAdapter`), the sole class touching `UnityEngine.SceneManagement.SceneManager`. `LoadScenesAsync(IReadOnlyList<int> sceneIds, int activeSceneId, IProgress<float>, CancellationToken)` additively loads each id then, if `activeSceneId >= 0`, calls `SetActiveScene`; `UnLoadScenesAsync(IReadOnlyList<int>, IProgress<float>, CancellationToken)` unloads each. Both report progress and return `bool`. It is handed to `SceneState` as the `SceneLoadFunc`/`SceneUnLoadFunc` by `UsefulToolkitRuntimeInitializer`.
  - `Initialization/` — `UsefulToolkitRuntimeInitializer : InitializerBase` builds the whole thing: its `internal Initialize(IBlackBoard, IBlackBoardController)` (called by `RootGameCompositor` with the same `BlackBoard` as both faces; the inherited `Initialize(IBlackBoard)` only logs an error, since the read face alone cannot build `SceneState`) `new`s a `SceneState` (persistent ids = its own scene's build index, warned if that scene is not in Build Settings, plus an optional `_additionalPersistentSceneIndices` serialized array), registers it as `ISceneState` on `SceneBoard`, then wires the serialized `SceneLoader`'s two methods via `RegisterSceneLoader`. `GameCompositor.Awake` runs it first, before `RegisterChildBoards`, so other Initializers can already use `ISceneState` from their own `Awake`.
  - The `AutoGenerated.BuildScenes` / `NonBuildScenes` enums come from the Editor-side `SceneEnumGenerator` (`Editor/SceneSupport/`), regenerated whenever the Build Settings scene list changes.
  - **Wiring is the consumer's job.** The intended flow: `UsefulToolkit/Scene/GenerateUsefulPersistentScene` makes a resident boot scene whose `RootGameCompositor<…>` subclass runs `UsefulToolkitRuntimeInitializer` (→ `SceneState` + `SceneLoader` live) and registers every project ChildBoard. To leave the boot state there are two paths: set the Compositor's `_startScene` (`[ScenePopup]`) for a no-code single-scene overwrite-load once init finishes, **or** construct `SceneLoadService(blackBoard, groups)` in your own code and call `Initialize(startGroupIndex)` — `_startScene` does not do groups, so anything multi-scene still goes through `SceneLoadService`. Every non-persistent scene gets its own `<SceneName>Compositor : GameCompositor<…>` (Inject/Initialize only, no board registration) and must be entered with the persistent scene already loaded. `Assets/Code/Scripts/` is the sandbox stand-in: one asmdef per layer (`Sandbox.<Layer>.Runtime`), `SceneMarker` (one per scene, shows scene name + seconds alive, to see whether a shared scene was kept or reloaded), `SceneTransitionTester` — a test-only `InitializerBase` wired into the persistent scene's Compositor that drives `ISceneState` and `SceneLoadService` from `OnGUI` buttons — and the **Pause wiring, which is the working demonstration of cross-scene DI**: `PauseState` / `IPauseState` (BlackBoardLayer, carries `[RegisterBoard(typeof(PauseBoard))]`), `PauseManager` / `IPauseManager` (Application — owns the State; `new`ed with no BlackBoard, registers the State in `Initialize(IBlackBoard)`), `PauseInitializer` (persistent scene: `new`s the manager and calls `TryRegisterContent<IPauseManager>` in `Awake`, then `_pauseManager.Initialize(bb)` in `Initialize`), and `PauseButtonInitializer` (`IInjectable<IPauseManager>` + `OnGUI` buttons, placed in **both** `TitleScene` and `InGameScene`). That split — construct and register in `Awake`, initialize in `Initialize` — is what lets a State-owning Application class go through the container at all, since `TryRegisterContent` is `Collection`-phase-only while the BlackBoard only arrives at `Initialize`. Verified in play mode: both scenes' buttons receive the same persistent-scene `PauseManager` through the Root scope. (The old `SceneFlowTestBootstrap` / `SceneFlowTestGui` and the `UsefulToolkit/Test/Setup Scene Flow Test` editor menu are gone, as is the old `CompositorTestScene` harness.)
  - **Generated `<SceneName>Compositor` files live in `Assets/Code/Scripts/Initialization/`, not beside their scenes.** A Compositor must sit in the same assembly as any Initializer that calls `TryRegisterContent`: the Compositor holds each Initializer as a `[SerializeField]` while that Initializer calls `<ConcreteCompositor>.TryRegisterContent<T>(…)`, so the dependency runs both ways and cannot be split across two asmdefs. `Assets/Level` holds level-design assets only and never code, so pointing the generator's save directory at the layer folder is the normal case, not a workaround.

Before writing or reviewing code in this area, treat it as an actively-changing design — folder contents and APIs are still moving.

#### Composition root & initialization

`framework/Runtime/Initialization/` (asmdef `UsefulToolkit.Framework.Initialization.Runtime`, namespace `UsefulToolkit.Initialization`) is the toolkit's cross-package composition root — this is what used to be the `architecture` package.

- The composition root is a **three-level CRTP hierarchy**, one generated `<SceneName>Compositor` per scene (there is no separate `CompositionBase` — `GameCompositor` is the `MonoBehaviour` base):
  - `GameCompositor : MonoBehaviour` (non-generic, `abstract`) — holds `protected static IBlackBoard SharedBlackBoard` plus `TrySetSharedBlackBoard` / `ClearSharedBlackBoard`, and `internal static readonly CompositionContainer Container` — the one DI container every Compositor shares. Exists as the `TypeCache` enumeration point and the legitimately-global slot for both. There is exactly one root, so one shared BlackBoard and one container.
  - `GameCompositor<TSelf> : GameCompositor where TSelf : GameCompositor<TSelf>` (`[DefaultExecutionOrder(InitializeOrderConst.Compositor)]` = **-100**) — the per-scene root. `private static TSelf _instance` and `InitializePhase _phase` are per-closed-type / instance, so two live compositors of different types never clash; `typeof(TSelf)` doubles as this Compositor's **scope key** into the shared `Container`. `Awake` (`protected virtual`): duplicate-`_instance` guard → `_instance = this` → `AbortInitialize` if `SharedBlackBoard == null` (persistent scene not loaded first — aborting rather than merely stopping is what keeps later Initializers from being told the misleading "not in the collection phase") → `_phase = Collection`. `Start` (`protected virtual`): `_phase = Inject` → `InjectAll()` → `_phase = Initialize` → `InitializeAll(SharedBlackBoard)`. `OnDestroy` clears `_instance` and drops this type's container scope (Domain-Reload-off safety). `public static bool TryRegisterContent<T>(T)` (Initializers call it as `<ConcreteCompositor>.TryRegisterContent<T>(x)` — the concrete type name, resolving to `GameCompositor<ConcreteCompositor>`'s static; misuse outside the `Collection` phase is logged — `InitializePhase` is `None`/`Collection`/`Inject`/`Initialize`/`Aborted`) registers into `typeof(TSelf)`'s scope, rejecting a null `instance` — a destroyed `UnityEngine.Object` included, since `is null` alone would pass a fake null through — so a key is never occupied by nothing; a duplicate `T` in **either** that scope or the Root scope is an error that calls `AbortInitialize(reason)` (`_phase = Aborted`, `enabled = false`, one error log carrying the reason), so `InjectAll`/`InitializeAll` never run for that scene — the same type must never reach consumers through two paths. `Aborted` is a distinct phase precisely so that later Initializers registering in the same `Awake` sweep are told the initialization was aborted, rather than the misleading "not in the collection phase". `protected static bool TryGetContent<T>(out T)` (called from the generated `InjectAll`) resolves **own scope → Root scope and nothing else**: sibling scenes can never see each other's registrations, since only the persistent scene is guaranteed to already exist when another scene loads. `private protected static TrySetAsRootScope` / `ClearRootScope` exist for `RootGameCompositor` only. Abstract: `InjectAll` / `InitializeAll`. There is **no** non-generic `GameCompositor.TryRegisterContent`.
  - `RootGameCompositor<TSelf> : GameCompositor<TSelf> where TSelf : RootGameCompositor<TSelf>` — the **persistent scene only**. Adds `[SerializeField] UsefulToolkitRuntimeInitializer _runtimeInitializer`, `[SerializeField] [ScenePopup] string _startScene`, and `abstract RegisterChildBoards(IBlackBoardController)`. `Awake`: `new BlackBoard(new SceneBoard())` → `TrySetSharedBlackBoard` (fails+stops if a second root exists) → `TrySetAsRootScope()` (makes this type's container scope the fallback every other Compositor resolves against; on failure it rolls the shared BlackBoard back as well — the two are always set and cleared together, so a half-built root never sits in the shared slot) → `_runtimeInitializer.Initialize(bb, bb)` **first** → `base.Awake()` → `RegisterChildBoards(bb)`. `Start`: `base.Start()` then, if `_startScene` is set, `TransitionToStartSceneAsync().Forget()` — loads that single scene (no group support) via `ISceneState.RequestOverwriteLoadAsync(buildIndex, empty)` when it has a build index, else `#if UNITY_EDITOR` `EditorSceneManager.LoadSceneAsyncInPlayMode` additive + `SetActiveScene` (left untracked by `SceneState`, warned), else error. `OnDestroy` clears `SharedBlackBoard` and the Root scope (only if this instance built it). Both gates — board registration after `base.Awake()`, start-scene transition after `base.Start()` — test `CurrentPhase` (a `private protected` getter on `GameCompositor<TSelf>`), **not** `enabled`: an externally re-enabled Compositor must not transition to the start scene without having been injected.
  - **Board registration lives only in the persistent scene's `RootGameCompositor`.** Every other scene's `<SceneName>Compositor : GameCompositor<…>` is a pure Inject/Initialize unit — it reads the shared BlackBoard and registers nothing. Scene-owned States/Events are registered by that scene's Initializers into the already-present boards, scoped by `gameObject.scene.buildIndex`, and dropped on unload by `IBlackBoardController.OnSceneChanged`. Running a non-persistent scene standalone (no persistent scene loaded) is therefore an error by design; use the persistent scene's `_startScene` picker to enter it.
  - **BlackBoard vs. Container — which one carries what.** Read faces go through the BlackBoard: a State's `IStateGetter`-derived interface, an Event channel's `I*Channel<T>` subscribe face. A **write face** — the Application class that owns a State, or an interface exposing its operations — is deliberately *not* put on the BlackBoard (only the class that created a State — Application or EngineAdapter — may change it, and an Event channel is a place to register callbacks, not a way to send requests inward). Write faces are handed out through the Container as `IInjectable<T>` dependencies instead, and the Root-scope fallback is what lets a scene receive one built in the persistent scene. Example: the persistent scene's `PauseInitializer` creates `PauseManager`, calls `TryRegisterContent<IPauseManager>(…)`, and registers `PauseState` into `PauseBoard` as `IPauseState`; the InGame and OutGame button Initializers each just implement `IInjectable<IPauseManager>`, and the pause feature never learns which scene's button drives it.
- The `BlackBoard` is **not** put in the DI container — it is passed straight to every `Initialize(IBlackBoard)`. Only the read face travels that way; `IBlackBoardController` never leaves `RootGameCompositor` / `SceneState`.
- `InitializerBase : MonoBehaviour` — `Initialize(IBlackBoard)` + an `Initialized` flag. An Initializer creates the objects other Initializers need and registers them via `<ConcreteCompositor>.TryRegisterContent` in `Awake`, declares its own dependencies by implementing `IInjectable<T>` / `IInjectable<T1,T2>` / … (`Inject(...)` is called during the `Inject` phase), and does its real work in `Initialize`. The premise is that a given concrete Initializer/Compositor type is never run in two scenes at once — if two scenes need the same feature, split the feature into its own scene (or change the init route). `UsefulToolkitRuntimeInitializer` is the one Initializer `RootGameCompositor.Awake` calls directly, and `GameCompositorGenerator` deliberately excludes it from the generated `InitializeAll`.
- **Initializer ordering is declared with `[InitializeOrder(int)]`** (`UsefulToolkit.Attributes`, `framework/Runtime/Attributes/InitializeOrderAttribute.cs`) on the Initializer class. **Ascending — smaller runs first**, same convention as `InitializeOrderConst`, `DefaultExecutionOrder` and `FuncChainChannel`; a type without the attribute is treated as **0**, and ties fall back to type-FullName ordinal so generation stays deterministic. `AttributeUsage` is `Inherited = true`, so a package's abstract Initializer can fix the order for consumers' subclasses. The attribute is read by `GameCompositorGenerator` at generation time only — the ordering is baked into the generated `InjectAll` / `InitializeAll`, so **changing an order means regenerating every affected Compositor**; nothing detects a stale one. Orders other than 0 are emitted as a `// order: N` comment on the generated `Initialize` call. `input`'s **`InputInitializerBase`** carries `InitializeOrderConst.InitializerEarly` (-80) — on the abstract base, which is exactly what `Inherited = true` is for, since the concrete `InputInitializer` is generated into the consumer's assembly and must not have to re-declare it. That keeps the `InputState` it builds in existence before any consumer Initializer that reads it.
- `InitializableMonoBehaviour` (lives in `framework/Runtime/EngineAdapterLayer/Initialize/`, namespace `UsefulToolkit.Initialization`) — a `MonoBehaviour` that sets `enabled = false` in `Awake` until `Initialize()` re-enables it. `SceneLoader` derives from it. It has no ordering/`IComparable` member of its own; execution order is expressed with `[DefaultExecutionOrder]` and the `InitializeOrderConst` constants (`Compositor = -100`, `InitializerEarly/-Initializer/-InitializerLate = -80/-70/-60`, `DefaultEarly/-Default/-DefaultLate = -10/0/10`).

### Editor tooling internals

- Settings pages are discovered via reflection, not hard-wired: `SettingPageProvider` (`Framework/Editor/Setting/`) uses `InstanceCollector`/`TypeCollector` (`Framework/Editor/Reflection/`) to find all `SettingPageBase` subclasses and surfaces them as tabs in `UsefulToolkitSettings`. Adding a new settings tab means subclassing `SettingPageBase` — no registration step needed.

The generator decides root-ness by `SceneContainsRuntimeInitializer(scene)` (does the scene hold a `UsefulToolkitRuntimeInitializer`); only for a root scene does it collect every `ChildStateBoardBase` / `ChildEventBoardBase` concrete type in the project (minus `SceneBoard`, which `BlackBoard`'s constructor already takes) and emit `RegisterChildBoards`. `CollectInitializerFields` groups the scene's Initializers by concrete type and sorts them by `[InitializeOrder]` then FullName — that sort is the only thing deciding the generated call order, so an Initializer must never assume it runs after another without declaring it. It only warns about the generated file's asmdef references, it does not edit asmdefs.

### Project structure tool

`Framework/Editor/ProjectStructure/` reorganizes a consumer project's `Assets/` (typically a freshly-created Unity project, whose default layout differs per template — URP/2D/HDRP each ship a different set of files) into the toolkit's standard layout. Split across `ProjectStructureTemplate` (data) / `ProjectStructurePath` (path helpers) / `ProjectStructureTemplateIO` (JSON load/save) / `ProjectStructurePlanner` (builds a side-effect-free plan, i.e. the dry run) / `ProjectStructureApplier` (executes it) / `ProjectStructureSnapshot` (current `Assets/` → template) / `ProjectStructureWindow` (IMGUI).

- The template is **JSON, not a ScriptableObject**, so it can be shipped inside the package and carried between projects. `DefaultTemplate.json` sits next to the code and is overridden per-project by `ProjectSettings/UsefulToolkitProjectStructure.json` (kept outside `Assets/` so the tool never processes its own config). Parsed with `JsonUtility`, so **no comments are allowed** — the `description` field is where notes go.
- Rules are `{match, pattern, action, destination}` and are evaluated in the fixed order **ExactPath → Folder → Glob → Name**; a target claimed by an earlier rule (including everything under a claimed folder) is never re-evaluated. That ordering is load-bearing: it is what lets `Assets/Readme.asset`'s Delete rule win over the broad `Assets/*.asset` Glob.
- `excludes` blocks a path from being a move *source* and from snapshot scanning, but still allows it as a *destination* — that's how `Assets/Plugins` receives `TextMesh Pro` while its own contents stay untouched. Unity's special folders (`Resources`, `StreamingAssets`, `Editor`, …) are excluded by default because their location carries meaning.
- Everything goes through `AssetDatabase` (`MoveAsset`/`CreateFolder`/`MoveAssetToTrash`) so `.meta` files and GUID references survive; Delete sends to the OS trash rather than deleting outright. All moves are pre-checked with `ValidateMoveAsset` and **the whole run aborts before any move or delete if a single one fails**.
- Two ordering constraints in the planner are easy to reintroduce as bugs: folders that a folder-move will itself create must *not* be pre-created (`BuildFolderCreations` filters anything same-or-under a move destination, which is why `Assets/Data/Settings` appears in `folders` yet is skipped when `Assets/Settings` is being moved into `Assets/Data`), and moves are topologically ordered by `OrderMoves` so a move whose destination is still occupied by another move's source runs second.
- Snapshot can only emit `Name` rules (the current state doesn't record where anything came from), and it **skips any name that occurs at more than one path**, reporting it as a warning instead of guessing. Re-running it regenerates the `Name`+`Move` rules while preserving hand-written ExactPath/Folder/Glob rules.

### Input package

`Packages/com.rei.usefultoolkit.input/` is the reference example of a feature that crosses every layer. It has been rewritten three times, so treat anything contradicting the below as stale: it used to publish an `InputBoard` of type `ChildEventBoardBase` (gone — `InputBoard` is a `ChildStateBoardBase`), it used to hang an `IInputDispatcher` off `IInputState` that carried the mutating calls (gone), and until the latest rewrite `InputState` kept its own `ActionChannel` per `(map, action)` together with `Bind`, `RegisterInputAsync`, `IExternalInputSource` and `MobileInputEngineAdapter` — **all of that is deleted**, because it re-implemented what `InputAction` already does. The design discussion behind the current shape is in `Assets/LocalAssets/UsefulToolkit/入力パッケージ 再設計 作業手順書.md` (its later phases changed during implementation; this section is the authority).

**Rule 1: through the BlackBoard you may only read the current state and register input callbacks. Nothing reachable from the BlackBoard can change the State.** The read face `IInputState` goes on the board; the write face `IInputController` is handed out through the Compositor's DI container instead, and only the Application class holds the concrete `InputState`.

**Rule 2: do not re-implement InputSystem.** `InputState` owns only what State-Centrism requires it to own — which action maps are active and whether input is enabled — and forwards everything else. Callbacks attach straight to the `InputAction`; external input enters at the **device layer** as a generated virtual device, so it arrives as a real `InputAction` and map gating, rebinding, `InputActionTrace` and `InputEventTrace` replay all apply to it unchanged. Before adding a mechanism here, check whether InputSystem already has it.

- `Runtime/BlackBoardLayer/` (namespace `UsefulToolkit.BlackBoard.Input`) — `InputBoard` (an empty `ChildStateBoardBase`), `InputState`, `InputContext<TValue>` / `InputPhase` (this layer's own phase enum, so the payload never drags `InputSystem` into the BlackBoard), and four interfaces that divide the surface up:
  - **`IInputState`** (`IStateGetter`-derived — the only thing published to the board): `InputEnabled`, `ActiveActionMaps` (`IReadOnlyList<string>`), `IsActionMapActive(Enum)` **and** `IsActionMapActive<TMap>(TMap) where TMap : struct, Enum`, `ReadValue<TValue>(Enum, Enum)`, `RegisterInput<TValue>(Enum, Enum, Action<InputContext<TValue>>)` → `IDisposable`, `RegisterEventOnInputEnabledChanged(ActionEntry<StateContext<bool>>)`, `RegisterEventOnActiveActionMapsChanged(ActionEntry)`. `ReadValue` is not a convenience: some devices misreport phases (Meta Quest 3S XR controllers repeat started/canceled for as long as an input is held), so polling must stay possible.
  - **`IInputController`** (never on the board): `SwitchActionMap` / `EnableActionMap` / `DisableActionMap`, `EnableInput` / `DisableInput`, `WriteExternalInput<TValue>(Enum slot, TValue value)`. It is defined in the BlackBoardLayer only because that is the one place both Application and EngineAdapter can see (same reason as `IInputEngineBridge`) — **its location is not permission to put it on a board**.
  - **`IInputEngineBridge`** — what an EngineAdapterLayer class implements: `ReadValue<TValue>`, `Subscribe<TValue>(Enum, Enum, Action<InputContext<TValue>>)` → `IDisposable` (attach a handler to the action's started/performed/canceled; an unresolved action returns `BoardDispose.Empty`), and **two** reflect-to-engine methods: `Apply(bool inputEnabled, IReadOnlyList<string> activeActionMaps)` is **differential** — it only disables maps not in the list and only enables maps not already on, so an in-progress input on an untouched map is not interrupted (used by `EnableActionMap` / `DisableActionMap` / `EnableInput` / `DisableInput`); `ApplyExclusive(bool, IReadOnlyList<string>)` disables **every** map then re-enables the listed ones, deliberately re-arming even maps that stay active so their in-progress input is cancelled (used by `SwitchActionMap` and by `RegisterInputEngine` on connect, since the engine's pre-connect map state is unknown). There is deliberately **no engine→State path**.
  - **`IExternalInputDeviceBridge`** — `bool TryWrite<TValue>(Enum slot, TValue value)`. Implemented by **generated** code (see "External input" below), since the virtual device type lives in the consumer's assembly.
- `InputState` derives `GameStateBase`, carries `[RegisterBoard(typeof(InputBoard))]`, and implements `IInputState` plus the mutating half. Its fields are the active-map list, the enabled flag, the two change-notification lists, the engine bridge and the external-device bridge — **it holds no registration table at all**:
  - `RegisterInput` validates its arguments and forwards to `_engine.Subscribe`, returning that `IDisposable` as-is (no engine connected → warning + `BoardDispose.Empty`). Keeping a table here would be a second hub in front of `InputAction`'s own, and would put registrations into the State the BlackBoard exposes.
  - **Value-type mismatches are detected at fire time, not at registration time**: `InputAction.CallbackContext.ReadValue<TValue>` throws when `TValue` does not match the action. The action's `expectedControlType` in the asset is the single source of truth for the type; nothing here re-checks it.
  - `RegisterInput` is deliberately **not** split per phase: one callback receives started/performed/canceled and the consumer branches on `InputContext<TValue>.Phase`.
  - **Null policy, applied consistently**: a query returns a safe default (`IsActionMapActive` → `false`, `ReadValue` → `InputPhase.Disabled`); a command throws `ArgumentNullException`.
  - `RegisterInputEngine(IInputEngineBridge)` and `RegisterExternalInputDevice(IExternalInputDeviceBridge)` are on the concrete class only, not on `IInputState` — same pattern as `SceneState.RegisterSceneLoader`. `RegisterInputEngine` pushes the current state into the engine on connect, which is what makes "engine is a mirror" hold from the first frame. `WriteExternalInput` with no device bridge connected is a warning and a no-op.
  - **Disposing what `RegisterInput` returns is the caller's job, by design.** There is no scene-scoped overload: common input often spans scenes. `InputUserInitializerBase` (`Runtime/Initialization/`) collects registrations made through its own `RegisterInput` and disposes them in `OnDestroy`; plain `MonoBehaviour`s can use UniTask's `AddTo(this.GetCancellationTokenOnDestroy())`.
- **Zero-allocation on the per-frame paths.** `EnumNameCache` / `EnumNameCache<TEnum>` (`framework`'s `Runtime/Utility/`) replace `Enum.ToString()`, which allocates ~30 B a call in Mono; `InputDispatcher` caches `(Enum, Enum) → InputAction` so name resolution, the `FindActionMap`/`FindAction` scan and the not-found warning all happen once per pair; the generated device bridge reinterprets `TValue` with `UnsafeUtility.As` instead of boxing. The one cost left is at the **call site**: passing an enum literal to an `Enum` parameter boxes it, so a per-frame `ReadValue` should hold `private static readonly Enum` fields (documented on `IInputState.ReadValue`). `IsActionMapActive` needs nothing — its generic overload wins overload resolution automatically.
- `Runtime/Application/` — `IInputManager : IInputController` / `InputManager` (`[Serializable]`, parameterless ctor, since the Initializer holds it by `[SerializeReference]`): `bool Initialize(IBlackBoard, IInputEngineBridge, IExternalInputDeviceBridge externalInputDevice)` creates the `InputState`, hands it the engine bridge (and the device bridge when non-null — external input is optional), and registers it into `InputBoard` as `IInputState`; every `IInputController` member is a guarded delegation to that State. It **returns `false` without creating the State** if the engine bridge is null or `InputBoard` is not registered, and `InputInitializerBase` propagates that by not calling `base.Initialize` (so `Initialized` stays false) — the same "don't report success on failure" rule `UsefulToolkitRuntimeInitializer` follows. **The only class holding the concrete State**, per the "Application creates the State" rule.
- `Runtime/EngineAdapterLayer/` — `InputDispatcher : InitializableMonoBehaviour, IInputEngineBridge` is the sole class touching `InputActionAsset`, which it holds as a `[SerializeField]`. It has **no BlackBoard reference at all**. `Subscribe` adds one delegate to the `InputAction`'s three events and returns a `BoardDispose` that removes it — the action itself is the multicast hub. `Apply` / `ApplyExclusive` no-op the map toggling while `inputEnabled` is false, and `Apply` additionally warns for any requested map name that does not resolve (the differential path never calls `FindActionMap`, so that check is done separately).
- `Runtime/Initialization/` — **`InputInitializerBase`**, `abstract`, `[InitializeOrder(InitializeOrderConst.InitializerEarly)]`. Holds `[SerializeField] InputDispatcher` and `[SerializeReference] [SubclassSelector] IInputManager` defaulting to `new InputManager()`, exposes `protected IInputController Controller`, and `protected virtual IExternalInputDeviceBridge CreateExternalInputBridge() => null` for the generated subclass to override. **Order inside `Initialize` is fixed and load-bearing**: `_inputDispatcher.Initialize()` runs *first*, because `_inputManager.Initialize(...)` ends up calling `RegisterInputEngine`, which immediately pushes state into the engine — the `InputActionAsset` has to be usable by then. `InputUserInitializerBase` (`[InitializeOrder(InitializeOrderConst.Initializer)]`) is the consumer-facing base for Initializers that only register callbacks: it resolves `IInputState` off `InputBoard`, then calls `OnInputReady()`, where the subclass calls its `RegisterInput` / `ReadValue` helpers.
- The **concrete `InputInitializer` is generated into the consumer's assembly**, not shipped: `TryRegisterContent` only compiles against the generated Compositor's concrete type, which the package cannot see. `Editor/InputInitializerTemplateProvider.cs` emits a thin subclass whose `Awake` does `<Compositor>.TryRegisterContent(Controller)`, whose `Initialize` is where the consumer writes the starting `SwitchActionMap`, and which carries a commented-out `CreateExternalInputBridge` override to enable once a virtual device is generated. `Editor/InputPersistentSceneContributor.cs` then adds `InputDispatcher` to the `UsefulToolkit System` root and assigns it into that Initializer's `_inputDispatcher` (reached through the abstract base, since the generated type is invisible from the package assembly). Assigning the `InputActionAsset` stays manual.
- `map` / `action` are `System.Enum` across the whole public surface and `InputState` converts them to name strings internally, so no package here depends on a consumer type. This is also why Unity's own "Generate C# Class" is not used: its `I<Map>Actions` interfaces change shape whenever an action is added or removed, forcing every implementer to be rewritten.
- `Editor/InputActionEnumGenerator.cs` (`UsefulToolkit/Input/Generate Action Enums`) regenerates `ActionMaps` plus one `<Map>Actions` enum per map. It **validates everything before writing anything**, so a rejected asset never leaves a half-updated set of files: a name needing sanitizing is a warning (the runtime lookup uses the original name, so the generated enum would not match it), and two names collapsing to one identifier is an error that aborts the run. `Editor/InputActionAssetPostprocessor.cs` auto-runs it, but **only for the Project-wide Actions asset** — output file names are derived from the enum name alone, so importing a second `.inputactions` would overwrite the first one's files. Renaming an action therefore regenerates the enum and turns every stale use into a compile error.

#### External input (generated virtual device)

The one thing neither InputSystem bindings nor uGUI can express is **assigning meaning to touches that share an area** — e.g. "a long-press anywhere slides, a tap anywhere attacks". `<Touchscreen>/touch0` etc. keep a slot for one touch's lifetime, but which slot carries which gesture depends on what else was down, and uGUI routes both gestures to the same element. Code that arbitrates this still produces control-shaped values, so it feeds them into a **virtual device** rather than into a side channel.

- **Declaration** — `ExternalInputDefinition` (`Runtime/ExternalLayer/`, namespace `UsefulToolkit.External.Input`, `Create > UsefulToolkit > Input > External Input Definition`): a list of `ExternalInputSlot { Id, Name, ExternalInputValueType }` with value types `Vector2` / `Vector3` / `Quaternion` / `Axis` (float) / `Button` (bool) / `Integer` (int). `Id` is a hidden GUID filled in by `OnBeforeSerialize` / `OnValidate`; **never change it** — it is what lets a rename be told apart from delete-and-add.
- **Generation** — `UsefulToolkit/Input/Generate External Input Device` (`ExternalInputDeviceGenerator.Generate(definition, bool interactive = true)`; pass `interactive: false` from scripts, since the rename confirmation is a modal dialog). Slot names must be identifiers, unique **case-insensitively** (InputSystem control names are case-insensitive, so two such slots would collide in the layout), and carry an Id. Output goes to two places:
  - `Runtime/Input/ExternalInputs.cs` — the slot enum, next to `ActionMaps` in the enum-only assembly (`AutoGenerated.Runtime` in the sandbox). That assembly must stay reference-free so any layer, ExternalLayer included, can use the enums.
  - `Runtime/InputDevice/` — its own generated asmdef `<Namespace>.InputDevice.Runtime` (references `Unity.InputSystem`, `UsefulToolkit.Input.BlackBoard.Runtime` and the enum assembly) plus `UsefulInputState`, `UsefulInputDevice`, `UsefulInputDeviceRegistration` and `UsefulInputDeviceBridge`. If the `Input` folder has no covering asmdef, the enum is emitted here instead (Assembly-CSharp cannot be referenced from an asmdef).
  - The layout is registered as **`UsefulInput`**, from both `[InitializeOnLoad]` and `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` — the Editor registration is what makes `<UsefulInput>/<SlotName>` appear in the binding picker.
  - **Every slot is one field; `Button` is a `float` with `format = "FLT"`, not a bit.** `QueueDeltaStateEvent` cannot target bitfield controls, and each write targets exactly one control so several writers never clobber each other. `Button` slots accept `bool` (written as `1f` / `0f`); every other type accepts its field type. A mismatch is an error log and the write is dropped.
- **Consumer wiring** — add a reference to `<Namespace>.InputDevice.Runtime` in the asmdef that holds `InputInitializer` (the generator warns if it is missing; it **creates** the device asmdef but never edits a consumer asmdef), then enable the `CreateExternalInputBridge() => new UsefulInputDeviceBridge()` override. After that, bind actions to `<UsefulInput>/<SlotName>` in the asset and write with `IInputController.WriteExternalInput(ExternalInputs.X, value)`.
- **Rename following** — `ExternalInputManifest` stores the last generated `Id → Name` in `ProjectSettings/UsefulToolkitExternalInput.json` (missing = first run; unreadable = abort, since a missed rename would silently break bindings). `ExternalInputBindingPatcher` diffs it against the declaration and rewrites `"path": "<UsefulInput>/<OldName>` (followed by `"` or `/`, matched case-insensitively) in **every `.inputactions` under `Assets/`**. It is a **text** replacement, not an InputSystem API round-trip, so the diff is only the affected lines and a file's BOM is preserved. All renames run as **one** regex pass — replacing them one by one would collapse a swap (A↔B) into a single name. The whole plan is built before any write, and a file that cannot be read aborts the run. Before rewriting, generation aborts if an Input Actions editor window is open (it would save stale contents over the rewrite), and the interactive path shows a confirmation listing the counts and warning that **runtime rebinding overrides (`SaveBindingOverridesAsJson` output) cannot follow**. A removed slot is only a warning listing the bindings still pointing at it — except when a live slot now carries that name, in which case the binding is live and nothing is reported. A rename / revert / swap round-trip has been verified to leave the `.inputactions` byte-identical.

The sandbox exercises both paths: `Assets/Code/Scripts/Initialization/InputStateTester.cs` (persistent scene) drives `IInputState` / `IInputController`, and `ExternalInputTester` + the generated `ExternalInputTestCompositor` sit in `Assets/Level/Scenes/Test/ExternalInputTest.unity` (entered through the persistent Compositor's `_startScene`, which currently points at it), writing to the slots declared in `Assets/Data/Input/ExternalInputDefinition.asset`, which the asset's `ExternalTest` map binds as `Move` → `<UsefulInput>/MoveStick` and `Attack` → `<UsefulInput>/Attack`. That scene deliberately lives under `Assets/Level/` rather than `Assets/Code/Test/`: the latter is gitignored, which would leave the tracked Build Settings entry, the `BuildScenes` enum and `_startScene` all pointing at a file a fresh clone does not have.

### Mesh cut package

`Packages/com.rei.usefultoolkit.meshcut/` slices several meshes at once with a single plane, entirely inside `[BurstCompile]`d jobs — vertex side classification, face split, cap (cut-face) generation, and collider sampling. Only the parts that require a Unity API (reading Transforms, creating `Mesh`es, placing colliders) stay on the main thread. Ported from `TaguchiRei/MeshCut` (`Packages/com.rei.usefulmeshcut`); the algorithm itself is unmodified, so upstream fixes can be diffed straight across. `README.md` in the package is the user-facing manual and `CHANGELOG.md` records exactly what the port changed.

- **It is not organized by State-Centrism layers.** It is a self-contained library with no State, no BlackBoard involvement, and no place in the layer table, so it keeps the source's `Runtime/{Components, Core, Data, Jobs}` split under a single `UsefulToolkit.MeshCut.Runtime` asmdef. Don't retrofit layer folders onto it.
- Runtime pieces: `MultiMeshCut` (the job chain; `Cut(CuttableObject[], NativePlane)` returns `CutMesh[i*2]` = front, `[i*2+1]` = back), `MultiCutBlade` (a scene component whose own Transform is the blade — position on the plane, `transform.up` the normal — and which applies results to pooled fragments; `ExecuteCut` returns `UniTask<MultiCutResult[]>`, one `{Original, Front, Back}` per target actually cut, in post-`FilterCuttable` order, only after every fragment has been fully applied — an empty array, never null, when nothing was cut), `MeshDataCache` + `NativeMeshDataStore` (the native mesh registry), `MeshCutObjectPool` (fragment pool), `CuttableObject` (target/fragment marker; also builds sphere colliders by k-means over the sampled points).
- **Every cut target must be registered with `MeshDataCache`** — `Start()` walks its **active** children (no `includeInactive`) to register meshes and assign `MeshId`; an unregistered object gets no id and produces broken results. Anything added at runtime or parked inactive (e.g. a pooled enemy body) goes through **`MeshDataCache.Register(CuttableObject)`** instead, which works on inactive objects and on objects outside the `MeshDataCache` hierarchy, and returns `false` before `Start()` has built the store. A mesh with Read/Write disabled is rejected with an explanatory error (`Register` returns `false`, `Initialize` skips it) instead of the opaque `ArgumentException` `NativeMeshDataStore.Add` would throw. Shared meshes are deduplicated through a `Mesh → id` dictionary that `Rebuild` remaps (entries with no surviving user are dropped), so re-registering the same prefab mesh never grows the store; a part currently showing its own cut mesh is added with its last submesh as the cap slot, so a later cut appends to it.
- **Cut-count limit** — `CuttableObject.MaxCutCount` (serialized, default 0 = unlimited) / `CutCount` are per *lineage* (a part plus every fragment born from it). A fragment inherits the source's limit and `CutCount + 1`; `CanCutFragments` (`CanMultiCut && (max == 0 || count + 1 < max)`) is what `MultiMeshCut.RegisterMultiCutFragments` checks, so a fragment that reaches the limit is never appended to the store and gets `DisableCutting` through the existing `-1` id path. The limit only applies when `CanMultiCut` is on — with it off the object is cut once, as before. `MultiCutBlade.OriginalSnapshot` carries both values because the source may be recycled mid-apply.
- **Adopting / restoring a shape** — `CuttableObject.AdoptCutShape(fragment)` moves a fragment's cut shape onto another object (typically the original part that stays on an enemy body): mesh **with ownership** (the fragment's `_ownedCutMesh` is nulled, so recycling it no longer destroys the mesh), materials (via a static `List<Material>` buffer, no allocation), cut settings and count, and cuttability (the fragment's `MeshId` + `RegisterUser`), and calls `DisableCutting` on the fragment. The target's collision depends on the `AdoptColliderMode` overload: `Spheres` (the one-argument overload's default) copies the fragment's sphere collider center/radius/enabled (growing the target's sphere list if the pool prefab has more) and disables the target's own colliders captured at init (`BoxCollider` etc. on the prefab); `FitOwnColliders` instead refits those own colliders (only the ones enabled at init — Box/Sphere/Capsule to enclose the adopted mesh's local `bounds`, MeshCollider gets the mesh itself, any other type is disabled), keeps them enabled and disables the spheres, falling back to `Spheres` with a warning when nothing could be fitted. That mode exists because k-means spheres are built from vertices only, so a long, low-poly part gets an uncovered stretch in the middle and an `OverlapBox` blade there finds nothing; pool fragments themselves still have that gap (documented as a known limitation in the README, not fixed). `RestoreInitialShape()` reverts to the mesh / materials / collider states **and shapes** (center/size/radius/height/direction/MeshCollider mesh, held per collider in the private `OwnColliderShape`) / cut settings captured at init, destroys only an owned cut mesh, zeroes the count, and leaves the object **not** cuttable — re-`Register` it. Neither changes active state. Initialization (`EnsureInitialized`, run from `Awake` and from these entry points) is one-shot so these also work on objects whose `Awake` has never run.
- `RecycleBuffer<T>` / `IRecyclable` are **not** in this package: they were moved to `framework`'s `Runtime/Utility/` (namespace and asmdef `UsefulToolkit.Utility`) during the port because nothing about them is mesh-specific. `MeshCutObjectPool` and `CuttableObject` reach them through that asmdef reference. `RingBuffer<T>` came from the same source project and lives there too, currently unused by any package.
- UniTask is a hard runtime dependency (`MultiMeshCut`/`MultiCutBlade`/`MeshCutObjectPool` await it) and is a git URL, so `package.json` cannot declare it — the `UsefulToolkitInstaller` entry carries it as a `RequiredDependencies` entry instead, the same way `Framework` does.

### VFX Graph tools

`aitool`'s `Editor/VfxGraph/` holds three uloop custom tools that let an external AI agent read and edit a VFX Graph (`.vfx`, and Subgraph `.vfxoperator` / `.vfxblock`) without touching its YAML, where every slot is its own object cross-referenced by `fileID`: `export-vfx-graph` (graph → Markdown + `Revision`), `edit-vfx-graph` (JSON operation list → graph) and `list-vfx-nodes` (search what can be added). All need a running Editor with the asset imported. One multi-tool skill, `Skill/SKILL.md` (`uloop-vfx-graph`), documents all three; it sits at `Editor/<ToolFolder>/Skill/SKILL.md`, the one location `uloop skills install` scans inside packages, so the tools cannot each have their own skill folder.

- **The folder is its own asmdef, `UsefulToolkit.Ai.VfxGraph.Editor`, which compiles only when unity-cli-loop V3 is installed** (`versionDefines` on `io.github.hatayama.uloopmcp` `3.0.0` → `USEFULTOOLKIT_ULOOP_V3`, used as a `defineConstraints`), so `aitool` itself never depends on uloop. It references `UnityCLILoop.ToolContracts` only — **not** the VFX Graph assemblies.
- **VFX Graph has no public authoring API.** Its editing model (`VisualEffectResource`, `VFXGraph`, `VFXContext`, `VFXBlock`, `VFXSlot`, `VFXParameter`, …) and the graph window's controllers are all `internal`, so everything is looked up by type name through `VfxGraphReflection`; a VFX Graph upgrade that renames those members surfaces as an error from the tool (and a failing EditMode test), not a compile error. `com.unity.visualeffectgraph` is pinned in `manifest.json` for that reason — rerun the tests whenever it is bumped.
- **IDs** (`VfxGraphNodeIds`, the only place they are assigned): contexts `c1`…, operators `o1`…, properties `p1`…, blocks `c1.b1`…, each by position in the graph. Because they are positional, export emits a `Revision` — the first 12 hex of SHA-1 over the sorted `id=ModelTypeFullName` pairs, deliberately **not** over the Markdown: which settings are shown depends on attribute usage collected only at graph compile time, so a content hash changed whenever the window compiled (or after a domain reload) and rejected valid edits. Edit refuses to run unless the caller's Revision matches the current graph; value or setting changes made in between are therefore not detected, only ID shifts. IDs in one operation list always refer to the graph as of that Revision; nodes added in the same list are referred to by `"as"` aliases (`$name`), and their resulting IDs are returned in `Aliases`.
- **Export** (`VfxGraphTextExporter`): `## Properties`, `## Systems` (contexts grouped by the `VFXData` they share), `## Operators`, `## Notes` (sticky notes, groups). Every input slot is printed, and `*` marks a value that differs from the node's `inputProperties` default (compared by formatted text). Links print as `<- o3.r`; a parameter's master slot name and an empty single-output name are dropped. Settings are the union of the `InInspector` and `InGraph` visible ones (`VfxGraphReflection.GetVisibleSettings`), named by their raw field names. An operator's type dropdown is **not** a visible setting (it is the hidden `m_Type` of `VFXOperatorDynamicType` / `VFXOperatorNumericUniform`, or the per-operand `m_Type[]` of `VFXOperatorNumericUnified`), so `GetOperandTypes` reads it through `IVFXOperatorUniform` / `IVFXOperatorNumericUnified` and export prints it as its own `Type:` / `Operand types:` line, with VFX's own `UserFriendlyName` (`float`, `Vector4`).
- **Edit** (`VfxGraphEditor`) **never writes the model directly — it goes through the open graph window's `VFXViewController`**, the same code the window's own UI runs (`AddNode`, `AddVFXParameter`, `VFXContextController.AddBlock(…, initSpace: true)`, `CreateLink` with its type adaptation, `RemoveElement`, port/parameter-controller `value` setters, `VFXContext.LinkTo`). That is what keeps parameter-node bookkeeping and dynamic-type operators consistent, and what puts the edit on the window's Undo stack. The asset is opened with `AssetDatabase.OpenAsset` (the double-click path) when no window shows it; a window showing another asset is never taken over. The whole list runs inside one Undo group named `AI: Edit <asset>`; any failure calls `Undo.RevertAllDownToGroup`, so a list is applied completely or not at all. Without `--save` the asset is left unsaved in the window for a human to review; `--save` calls the window's own `OnSave`. Before exporting the result it compiles the graph with `VFXGraph.RecompileIfNeeded(false, true)` (the window would only do so on its next update), so the returned Markdown already shows compile-dependent settings such as Update's `ageParticles`; a failed compile is reported in `Warnings`. Undo works only until the next domain reload, which resets the graph window's undo stack — a VFX Graph limitation that applies to manual edits too.
  - Controllers lag behind the model inside one call. A block added in the same list is not in its context controller's `blockControllers` until `ApplyChanges()` is called on that context controller (`NodeController` does that on a miss), and an operator whose slots are rebuilt by a type change (`Multiply` after its first Vector3 link) keeps stale ports until its node controller's `ApplyChanges()` — linking through a stale port leaves a link to a detached slot that later corrupts the graph. `SyncedPorts` therefore resyncs before every port lookup, and `VerifyNoDanglingLinks` rejects (and reverts) any list that leaves a link to an ownerless slot. Properties get a graph node (`AddVFXParameter(pos, parameterController, null)`) only when something is linked from them.
  - `setOperandType` mirrors the dropdown (`VFXMultiOperatorEdit`): `SetOperandType(type)` for uniform operators, `SetOperandType(index, type)` for unified ones plus the same propagation to `slotIndicesThatMustHaveSameType` (using `VFXUnifiedConstraintOperatorController.GetMatchingScalar`). Types are matched against the operator's `validTypes` by friendly name or `Type.Name`.
  - Values are converted from JSON by `VfxGraphEditor.ConvertValue`: primitives, enums by name, vectors as arrays, colors as `#hex` or arrays, `Gradient` / `AnimationCurve` objects, assets by path (`path:subAsset` for sub-assets), and VFX struct types (`Position`, `AABox`, …) as field objects merged over the current value — a single-field type also accepts the bare field value.
- **Node catalog** (`VfxNodeCatalog`): `VFXLibrary` descriptors and their sub-variants flattened, named with the same `DisplayName` cleanup as export (`|Set|_Lifetime|Random Uniform` → `Set Lifetime Random Uniform`) and with the `#1`-style ordering marks stripped from categories. `add*` operations match `type` against that name, case-insensitively and exactly, with an optional `category` substring to disambiguate.
- **Tests**: `Packages/com.rei.usefultoolkit.aitool/Tests/Editor/VfxGraphToolTests.cs` (asmdef `UsefulToolkit.Ai.Tests.Editor`, same uloop define constraint) drives the three tools through `IUnityCliLoopTool.ExecuteAsync`, the entry point uloop itself uses, against a copy of the package template `06_Firework.vfx` in a temporary `Assets/` folder. Teardown clears the window's `hasUnsavedChanges` (protected setter, set by reflection) before closing it, because closing a window with unsaved changes opens a save dialog that would block the run. Run with `uloop run-tests --filter-type assembly --filter-value UsefulToolkit.Ai.Tests.Editor`.
- Manual test inputs: the package templates (`Packages/com.unity.visualeffectgraph/Editor/Templates/*.vfx`, imported in place) and the `VFXGraphAdditions` sample copied into the gitignored `Assets/Code/Test/VfxExport/`.
- Not supported yet: reading a `.vfx` from git history, since only imported assets can be read.

## Conventions

- `UsefulToolkitInstaller`'s package list (`_packages` in `Packages/com.rei.usefultoolkit.framework/Editor/Setting/UsefulToolkitInstaller.cs`) uses `com.rei.usefultoolkit.*` sub-paths that match the real package folder names 1:1 (Framework, Debugging Tools, Git Support, Program Tools, Ai Agent Tools, Input, Networking, Quality Control Tools, Sound Art Tools, Visual Art Tools, Mesh Cut, Static Data Tools, WorkTrack — there is no `architecture` entry).
